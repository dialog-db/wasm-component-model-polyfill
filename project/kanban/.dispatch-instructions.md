# Dispatch instructions

You are the implementor for one card of this project's board. The card follows
these instructions. Deliver the card as commits on the branch checked out in
your workspace (`sandbox/<name>`); the pushed branch is the work product.

## Environment

- Enter the dev shell with `nix develop`, or prefix a command with
  `nix develop -c`. `menu` lists every project command. Build and test only
  through the menu: `build <profile>`, `tests native|web <profile>`,
  `tests all`, `lint`, `markdown format`. Do not run bare `cargo`. If the menu
  has no command for what you need, use the closest raw tool and say so in
  your report.
- Nix sees only tracked files. `git add` every new file before a `tests` or
  `lint` run, or the run measures a stale tree.
- Run one Nix lane at a time. This VM has 8 vCPUs and 16 GiB; a `tests` lane
  beside a `lint` exhausts it.
- The reference repositories are checked out at
  `~/Git/github.com/WebAssembly/component-model` and
  `~/Git/github.com/bytecodealliance/wasmtime`. They track upstream `main`
  as of the flake lock, not the corpus commits `tests/corpus/README.md`
  records. Check `git log -1` there before you rely on a commit; fetch an
  exact commit from `github.com`/`codeload.github.com` (both allowlisted)
  when the card names one.
- Read `CLAUDE.md` at the workspace root for the code conventions. Read
  `project/design/README.md` and the card's design document (its `PDDNNN`
  label names the file under `project/design/`) for the design contract.

## Acceptance gate

Report `done` only when all of the following hold:

1. Every acceptance criterion on the card is met in substance.
2. `tests all` is green on both targets (native and web). The conformance
   harness prints no `unexpected:` and no `stale expectation:` line.
3. `lint` is green.
4. `markdown format` has run if you changed a markdown document.

When your diff changes only documentation — markdown documents, doc comments,
or comments — and nothing in it can change a test's outcome, skip item 2. The
gate is then items 1, 3 and 4. Say in your report that you skipped `tests all`
and why. If any part of the diff could affect a test, run the full gate.

## Board

Never edit anything under `project/kanban/`. Do not tick the card's boxes. The
host writes the board from your report. Never edit anything under
`project/design/` either: the design corpus is the owner's. If the code you
write shows a design document is wrong or incomplete, say exactly what in your
report and the host routes it to the owner.

## Version control

- The workspace is a plain `git` clone. Use `git`, not `jj`.
- Commit with Conventional Commits: `type(scope): Sentence-case summary`. No
  trailers. No PDD numbers in messages.
- Push after every commit. A review round adds commits on top of the branch;
  never rebase, amend a pushed commit, or force-push.

## Reporting

- Before either report, stop every background job you started: wait for it or
  kill it, and confirm in the report text that nothing was left running.
- Never run `systemctl poweroff` or otherwise stop this VM. The host stops it
  after it has read your report; a VM that powers off before its terminal
  report loses the work's record.
- `report done "<summary>"`. The summary names the branch tip, says for each
  acceptance criterion how it is satisfied, lists the gate commands you ran
  with their results, and confirms nothing was left running.
- `report blocked "<what you need>"` when you cannot proceed. Say what you
  tried and what would unblock you.
