## What to build

File the issue below on Zena (https://github.com/elematic/zena/issues). The
owner files it, since an agent takes no action on GitHub. Once Zena fixes it,
the next pin move can drop the `as` casts in the demo's authoring library
(`rust/wcmp-demo/zena/authoring/element.zena`): the defaults of `request` and
`h`, and the fields `Element._attributes` and `Registry.#elements`.

Found on 2026-10-13 during card f6445b. With the pin at `43234db`, every demo
test stopped at the step "elements", because no element compiled. The demo now
casts each such value (`fix(demo): Cast new Map defaults and fields that Zena
now refuses`). `tests zena` did not catch the failure, because no scenario has
such a default or field.

### Proposed issue text

> **Title:** `zir unsupported` for a `new Map` given straight to a field or
> default of type `Map`
>
> At `43234db086afd2ae521415659b169db467b7d023` (main, 2026-10-13),
> `zena build` fails when a `new Map<K, V>()` fills a slot of the `Map<K, V>`
> interface type directly, as a field's value or as a parameter's default. Both
> programs below build at `1ac5684`, so it is a regression in
> `1ac5684..43234db`.
>
> ```zena
> class Element {}
> export final class Registry {
>   #elements: Map<u32, Element> = new Map<u32, Element>();
>   new() {}
>   count(): i32 { return this.#elements.size; }
> }
> export let main = (): i32 => new Registry().count();
> ```
>
> ```
> Error: the compiler failed on issue.zena: zir unsupported: constructor field
> type @Registry_s4733.<constructor> [in Registry_s4733.<constructor>]
> ```
>
> ```zena
> function take(m: Map<String, String> = new Map<String, String>()): i32 {
>   return 1;
> }
> export let main = (): i32 => take();
> ```
>
> ```
> Error: the compiler failed on issue2.zena: zir unsupported: call argument
> type @main [in main]
> ```
>
> The field fails the same way when it is public, when the constructor's
> initializer list assigns it, and for other key and value types. The default
> fails in a function and in a closure. A `let` that holds the `new Map` and is
> then passed or assigned compiles.
>
> The same failure for `Array` is older: it already happens at `1ac5684`, for a
> parameter `a: Array<String> = new GrowableArray<String>()` and for a field
> `a: Array<String> = []`.
>
> The failure comes from `LoweringContext.conformToSlot`
> (`lowering-context.zena`), called with `'constructor field type'` or
> `'call argument type'`. The value's type does not conform to the interface
> slot, and it is not a supertype that a `ref.cast` could narrow. So these two
> paths seem to miss the class-to-interface conversion that other assignments
> make.
>
> Workaround: cast the value to the slot's type, as in
> `new Map<String, String>() as Map<String, String>`, or let a field's type be
> inferred.
