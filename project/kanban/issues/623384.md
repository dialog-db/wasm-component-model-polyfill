## What to build

`Accessor::with` returns the closure's value, as Wasmtime's does, and a new
`Accessor::try_with` keeps today's `Result`.

The polyfill's `Accessor::with` returns `wcmp::Result<R>`, where Wasmtime's
returns the closure's value `R`. PDD028's "Both Targets" lists the `?` this
adds at each call site. The `wasi:webgpu` spike
(`~/Git/github.com/cdata/wasi-webgpu-test`, `rust/wasi-webgpu-wcmp/PORT.md`,
"Other edits") found a case the listed `?` does not cover. At `map-async`,
upstream's

```rust
accessor.with(|..| -> anyhow::Result<_> { .. })?;
```

still compiles against the polyfill, but the `?` takes off only the
polyfill's `Result`. The closure's own `anyhow::Result` is the statement's
value, and it is dropped. Only the `unused_must_use` lint warns.

With `with` in Wasmtime's shape, that line means the same on both runtimes:
the `?` is the closure's own. A reach that fails (outside any poll of the
store, with another store's token, or from inside another reach) panics in
`with`, as it does in Wasmtime. `try_with` is the polyfill's extension. It
returns the failure as the structured error it is today, so the polyfill's
own code, its tests of the refused reaches, and a host that wants no panic
use it. The extension is additive: code written for Wasmtime needs no
change to compile against it.

Neither "keep the `Result` and fail the compile" nor a lint the macro emits
works: on stable Rust, `with` cannot treat a closure that returns a `Result`
differently, and `bindgen!` cannot put a lint on a porter's own code.

## Acceptance criteria
- [x] `Accessor::with` returns the closure's value, and panics on a reach
      that fails, with the cause in the message.
- [x] `Accessor::try_with` returns `wcmp::Result<R>` with today's causes,
      and the tests of the refused reaches go through it on both targets.
- [x] The code `bindgen!` writes and the workspace's own calls use `with` or
      `try_with` as fits, and upstream's `accessor.with(..)?` at `map-async`
      no longer drops the closure's error (a test shows it).
- [x] PDD028's "Both Targets" no longer lists the `?` at `Accessor::with`,
      and the design that defines the accessor records the change.
- [x] `lint` passes, and `tests all` is green on both targets with the
      conformance summary unchanged.

## Review notes

- 2026-10-18 (owner, recorded by the implementer): Match Wasmtime's `with`
  and keep the `Result` in a polyfill-only `try_with`. A port of code
  written for Wasmtime then means the same on both runtimes, and the
  polyfill keeps its structured errors where it wants them. The cost is
  that a misused `with` panics, which aborts the page in a browser, as it
  panics in Wasmtime.

- 2026-10-18 (implementer): `Accessor::with` returns `R` and panics with
  the failed reach's error as its message; `Accessor::try_with` returns
  `wcmp::Result<R>` with the same causes. The 47 calls in `wcmp`'s own
  code, the code `bindgen!` writes (`host.try_with(..)?`), the guards'
  closes, and the drop handlers that detect a turn use `try_with`. Hosts
  in the workspace (bindgen tests, demo, smoke) use `with` as Wasmtime
  code would, which removed `??` and `.expect("reach ..")` there, and the
  dual-runtime test's two `answer` bodies are now the same (polyfill glue
  218 lines, Wasmtime glue 219). New accessor tests: `with` returns the
  value, a `?` after `with` passes on the closure's own error (the
  `map-async` shape), and, natively, `with` outside a poll panics with
  the store-not-in-poll message. PDD028 ("Access and Accessor", "Both
  Targets", "Revisions to Earlier Designs"), PDD020 (the accessor's
  pseudocode, rules, error model, and test cases), and PDD021 (the
  guard's close) are revised. `api update` recorded the surface. `lint`
  and `tests all` green.
