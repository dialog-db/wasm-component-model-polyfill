## What to build

Design debt the review of the boundary context named, for the next card that touches the crossing. First, `BoundaryContext::new` in `src/abi/context.rs` takes five inputs — options, instance, scope, the task tables, and the resource tables — where the reference's `LiftLowerContext(opts, inst, borrow_scope)` derives its handle table from the instance; the `instance` field is carried but dead. Make the context derive the tables from the instance (or the store) so a call site passes options, instance, and scope only. Second, `HandleTables::lend_to` (`src/resource/tables.rs` around line 217) honours a `Scope::Subtask` directly while `insert_borrow_for` (around line 267) falls back to the current task for the same argument; the two take the same parameter and treat it differently. Make both interpret the scope the same way, and state the rule in one place. Also: `invoke_trampoline` locks the ABI runtime state twice per call (`BoundaryOptions::resolve`, then the resource tables) where one lock could carry both; and `read_source_bytes` (`context.rs` around line 291) selects the destination's strategy for a source read.

## Acceptance criteria

- [ ] Every crossing builds its context from options, instance, and scope only, and the `instance` field has a reader.
- [ ] `lend_to` and `insert_borrow_for` treat a subtask scope identically, proved by a test.
- [ ] `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.
