## What to build
`tests web debug` and `tests web release` replay the nextest archive with nextest's default parallelism, one test process per CPU. Each browser test spawns a `wasm-bindgen-test-runner` (about 2 GB resident) plus a headless Chrome and a chromedriver. On a 32-core machine that is 32 runners and 32 browsers at once, and the kernel's OOM killer has taken down the whole session twice on 2026-09-15 (`Out of memory: Killed process ... (wasm-bindgen-te)` in the kernel log). The same run also hit `driver failed to bind port during startup` from chromedriver under that load.

There is a second, larger leak. Each `tests` invocation extracts the nextest archive (4 to 7 GB of debug test binaries) into `$TMPDIR` under the `nix develop` shell's temporary directory and never removes it, and `/tmp` is a 48 GB RAM-backed tmpfs. Six leftover extractions from dead sessions held 41 GB of RAM on 2026-09-15; deleting them took system memory use from 50 GB to 7 GB. Make `menuTestCommand` extract into a directory it removes when nextest exits (a `trap` on `EXIT`), or extract under the cargo target directory on disk instead of `/tmp`.

Cap the parallelism of the browser lanes in the flake's `menuTestCommand` (a `--test-threads` derived from available memory, or a fixed small number such as 4), keep native lanes at the default, and let an operator override it by passing `-j` after the leaf as today. Consider a `.config/nextest.toml` profile if nextest's per-binary settings fit better.

## Acceptance criteria
- [ ] `tests web debug` and `tests all` run with a bounded number of concurrent browser sessions by default.
- [ ] `tests web debug -j 8` still overrides the cap.
- [ ] Each `tests` run removes its extracted archive when it exits, on success and on failure.
- [ ] The README or menu description states the cap and why.
