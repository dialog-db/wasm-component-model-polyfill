## What to build
Card `c2c588` (landed as `679e060`) made `StoreContext::resource_drop` run a locally-defined destructor inside a turn. A destructor that blocks — for example on a synchronously lowered host `async` import whose future stays pending — now fails the release with the **stack-switch** cause (`SchedulerCause::StackSwitchNeeded`). That followed the owner decision on `c2c588`, but it departs from both references, and the owner has now decided to align with Wasmtime.

The spec says a destructor may not block: `CanonicalABI.md:3747-3748` ("destructors … may not block"), and a non-async-typed call that blocks before returning traps (`:3466-3469`). Wasmtime runs the destructor through `enter_guest_sync_call(false, instance)` (`crates/wasmtime/src/runtime/component/resources/any.rs:220`) and a block there traps with `Trap::CannotBlockSyncTask`. The polyfill already gives a synchronous-typed task the cannot-block cause (`src/baseline/sync_lower.rs:571` pins it). The difference is that `BoundaryCall::destructor` (`src/abi/boundary_call.rs:87-108`) never sets `may_not_suspend`, so the seam falls through to the stack-switch cause. The distinction matters: "stack switch" reads as "a suspend provider would let this block", and a future provider would then let destructors block, against the spec; "cannot block" says a destructor never may.

Make a destructor run as a task that may not suspend, so a block inside it fails with the cannot-block cause and Wasmtime's wording, on every target and whether or not a suspend provider is installed. Correct the docs that state the current rule: `Store::resource_drop` (`src/store/store.rs:235-251`, around `:240-246`) and `StoreContext::resource_drop` (`src/store/store_context.rs:284-289`) describe the failure as "a block a driver cannot serve". Update the test `it_fails_a_host_release_whose_destructor_blocks_on_a_pending_host_task` (`src/baseline/destructor_task.rs`) to expect the cannot-block cause.

While in the file, close the gaps `c2c588`'s reviewer named: assert `scheduler().host_task_count() == 0` after the failed release; add a destructor that calls an asynchronously lowered import (the case `Store::resource_drop`'s doc describes at `:247-249`, which has no test); and add a destructor that enters a driver and meets the recursive-driver cause.

## Acceptance criteria
- [ ] A destructor that blocks fails the release with the cannot-block cause (`SchedulerCause::CannotBlock` or the variant the polyfill uses for a synchronous task), carrying Wasmtime's `CannotBlockSyncTask` wording, on both targets.
- [ ] The same holds with a suspend provider installed, proved by a test using the seam's provider harness.
- [ ] The docs of `Store::resource_drop` and `StoreContext::resource_drop` state that a destructor may not block and cite the rule's source.
- [ ] Tests cover an asynchronously lowered import in a destructor, a driver entered from a destructor, and no host task left after a failed release.
- [ ] `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.


## Owner decisions
- 2026-09-22T22:15:50Z The owner decided to align with Wasmtime: a destructor runs as a task that may not suspend, and a block inside it fails with the cannot-block cause. This supersedes the stack-switch outcome card c2c588 shipped under its own owner decision.
