## What to build
The web debug lane runs 32 tests in flight in one shared headless Chrome (one per gigabyte of available memory, capped at the core count). On 2026-10-02 a new Zena test that ran five compiles of the compiler component in one instance, then instantiated and called each result, made the lane stall intermittently: a *different* Zena test that uses the compiler component (`it_compiles_one_source_to_the_same_bytes_in_one_instance_and_in_a_new_one`, `it_records_compile_for_every_subject_of_a_program_zena_refuses`, `it_reports_a_mismatch_when_one_result_of_a_passing_scenario_changes`) hit the runner's 180 s timeout as the last test of the run.

Evidence:
- With the new test at 32 in flight: 3 failures in 6 runs. Without it: 6 of 6 passed, at the tip and at the commit before.
- With the new test at `-j 16`: 3 of 3 passed, about 3 s slower in total.
- The JS heap of a page with the cached compiler is about 6 MB above the stock compiler, so retained memory alone does not explain it.

The test was made native-only. The cause is unknown: renderer process sharing between tabs, CPU starvation of a test's timers, or a wedge in the runner. Find it, and either fix it or size the lane's parallelism for compiler-heavy tests, so the next such test does not have to leave the web lane.

## Acceptance criteria
- [x] The stall is reproduced on purpose and its cause named.
- [x] Either the cause is fixed, or the web lane's parallelism accounts for it, and the session test runs on the web too.
- [x] Ten consecutive `tests web debug` runs pass.

## Review notes

- 2026-10-05 cause found and fixed in `fix(tests): Turn off the Chrome samplers that crash renderers running wasm`.
  - Cause: Chromium 154's allocation samplers, the in-process heap profiler (`HeapProfilerReporting`) and GWP-ASan (`GwpAsanMalloc`, `GwpAsanPartitionAlloc`), capture a native stack with `base::debug::TraceStackFramePointers`, which segfaults on V8's wasm frames when a Liftoff recompile in a wasm deoptimization allocates (`coredumpctl`: `SamplingHeapProfiler::CaptureNativeStack` and `gwp_asan::GuardedPageAllocator::Allocate` frames, `type=renderer`). The renderers running the Zena compiler die and their tests wait out the 180 s runner timeout; the pool held 2 renderers and idle CPU during the stall (sampled), so it was neither CPU starvation nor renderer sharing (34 renderers at 32 in flight).
  - Reproduced: with the session test back on the web lane, 3 of 6 `tests web debug` runs at 32 in flight failed (15, 2, 1 Zena tests) with 11 renderer cores. On purpose: `--enable-features=HeapProfilerReporting:renderer-prob-pct/100/...` makes `-E 'binary(zena)'` lose 15 tests with 8 cores; with the three features off it passes 39/39.
  - Fix: `WBG_POOL_BROWSER_ARGS` in the dev shells (repeating wbg-pool's own three `--disable-features` entries, since Chrome keeps the last one), the WebDriver config the smoke check uses, and the demo lane's session. The session test runs on the web lane again.
  - Ten consecutive `tests web debug` runs at 32 in flight after the fix: 1630/1630 each, about 48 s, no Chromium core dumps.
- 2026-10-05 gate at tip `22f57241c` (after the context-free review's fixes): `tests all` green on every lane (native debug/release/no-provider/wasmi, web debug/release/no-provider, fidelity x3, zena, demo); `nix flake check` of the committed rev green (`lint` in the working copy fails only `markdown` on the owner's uncommitted README.md); `tests smoke native`, `check`, and `webkit` 26/26. Conformance native 2409/2440, unchanged.
