## What to build
The web debug lane runs 32 tests in flight in one shared headless Chrome (one per gigabyte of available memory, capped at the core count). On 2026-10-02 a new Zena test that ran five compiles of the compiler component in one instance, then instantiated and called each result, made the lane stall intermittently: a *different* Zena test that uses the compiler component (`it_compiles_one_source_to_the_same_bytes_in_one_instance_and_in_a_new_one`, `it_records_compile_for_every_subject_of_a_program_zena_refuses`, `it_reports_a_mismatch_when_one_result_of_a_passing_scenario_changes`) hit the runner's 180 s timeout as the last test of the run.

Evidence:
- With the new test at 32 in flight: 3 failures in 6 runs. Without it: 6 of 6 passed, at the tip and at the commit before.
- With the new test at `-j 16`: 3 of 3 passed, about 3 s slower in total.
- The JS heap of a page with the cached compiler is about 6 MB above the stock compiler, so retained memory alone does not explain it.

The test was made native-only. The cause is unknown: renderer process sharing between tabs, CPU starvation of a test's timers, or a wedge in the runner. Find it, and either fix it or size the lane's parallelism for compiler-heavy tests, so the next such test does not have to leave the web lane.

## Acceptance criteria
- [ ] The stall is reproduced on purpose and its cause named.
- [ ] Either the cause is fixed, or the web lane's parallelism accounts for it, and the session test runs on the web too.
- [ ] Ten consecutive `tests web debug` runs pass.
