## What to build

Add one step to the smoke test in `rust/wcmp-smoke/src/lib.rs` that shows a capability only the concurrency runtime model makes possible, on both targets, with evidence a reader can check. No guest-side asynchronous built-in exists yet, so the example is host-driven. (Owner's decision, 2026-09-18: the host-task step originally asked for here needs internals — `start_host_task`, `HostTask`, the seam — that PDD018 keeps private until a host-async registration entry exists; it is re-filed as `a8c03d` to follow that entry and is not part of this card.)

A step named for what it shows, for example `run_concurrent waits outside the store`: with the store idle, call `Store::run_concurrent` with a closure that reads the host data through the accessor, awaits a genuinely external future — a short timer: `tokio::time::sleep` natively and a `setTimeout`-backed `JsFuture` in the browser, each behind the same per-target shape the crate already uses for the yield wake — then reads the host data again and returns a value. The evidence line records that the entry returned pending rather than the deadlock cause while the closure waited (poll it by hand once with a counting waker natively, as `it_returns_pending_when_the_store_is_idle_and_the_closure_waits_outside_it` does; in the browser, that the page stayed responsive across the wait), and the value it returned. Model it on `tests/baseline_run_concurrent.rs`.

Keep each step self-contained like the others (its own store, its own outcome), keep the module doc's list of what the smoke walks in step with the new step, and keep the page (`web/index.html`, `web/check.py`) reporting it. The smoke is not a test lane: it must build and run green under `smoke native` and `smoke web`, and the `smoke-web` flake check must pass. Do not widen the crate's public API: the step uses only what `lib.rs` already re-exports (`Store::run_concurrent`, `Accessor`).

## Acceptance criteria
