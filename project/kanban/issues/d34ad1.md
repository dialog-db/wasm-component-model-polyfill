## What to build
Name one suspend capability on the scheduler: a blocking built-in asks the scheduler to suspend the current guest thread until a readiness condition holds. The capability is a seam a target fills. This card fills it on neither target, so the seam has a provider slot and no provider. When the capability is absent, the seam runs a nested turn from inside the guest call: it runs ready guest work in other tasks and polls the host tasks the executor woke, with the waker of the outer turn, until the condition holds or nothing can progress. A host task that stays pending inside a nested turn stays in the store for the outer turn, so no wake is lost. If the nested turn goes idle with the condition unmet, the built-in traps: a task that must not block gets the cannot-block cause, which is the rule of the reference, and a task that is allowed to block gets the stack-switch cause, because the reference permits the block and only the target cannot serve it. A nested executor that blocks the native thread is ruled out: it deadlocks under a current-thread executor, tokio forbids it inside a runtime, and it has no browser counterpart. A nested turn is not a driver, so the recursive-driver rule does not apply to it. Shape the seam for a later JSPI provider: when the capability is present, guest code is entered only from the scheduler and never from inside a trampoline, except a frame that cannot block, a synchronous resource destructor or a `post-return` run from a trampoline; and a suspended thread resumes outside any poll of a driver, so the scheduler's state must be reachable from a trampoline without a driver on the stack. The blocking built-ins, JSPI, and a native fiber are out of scope.

## Acceptance criteria
- [ ] A test asks the seam to suspend until a host task completes, with no provider, and shows the nested turn polls the host task with the outer waker and returns when the condition holds.
- [ ] A test shows the nested turn runs ready work of another task while the condition is unmet.
- [ ] A test shows a host task left pending by a nested turn stays in the store and completes in the outer driver's later turn.
- [ ] A test with the condition unmet and nothing to progress gets the cannot-block cause when the task must not block, and the stack-switch cause when it may block.
- [ ] A test shows a nested turn from inside a driver's turn does not raise the recursive-driver cause.
- [ ] A test shows the seam consults the provider slot before it falls back to the nested turn.
- [ ] The scheduler's state is reachable without a driver on the stack, proved by a test that reads it from a host function called by the guest.
- [ ] The tests run on both targets.
