## What to build

Follow-up from the second review of the PDD027 series. When the host releases a handle it holds, run the destructor of the registration the handle came through, as Wasmtime does.

- **Today:** the store keeps one destructor per resource identity, and the first registration wins (`rust/wcmp/src/store/store_data.rs:232`, `entry(..).or_insert`). `ResourceAny::resource_drop` runs that one (`src/store/store_context.rs`, `resource_drop`). A guest's `resource.drop` runs the destructor of the import it holds the type through (`src/executor/trampoline.rs`, the destructor recorded per resource table).
- **Scenario:** interfaces A and B both register `ResourceType::host::<File>()`, with `dtor_a` and `dtor_b`, and B is registered first. A guest's drop of a handle it got through A runs `dtor_a`. The host's `ResourceAny::resource_drop` of the same handle, lifted through A, runs `dtor_b`.
- **Wasmtime:** records the destructor on each host-table slot when it lifts an `own` (`crates/wasmtime/src/runtime/component/resources/any.rs:264-265`, `host_tables.rs:206-210` at `v49.0.0-rc.1`), so a release runs the destructor of the slot.
- **Why now:** this became reachable in the PDD027 series. Before it, one shared identity meant one shared `HostResource` with one destructor.

Record the destructor, or the registration it belongs to, on the host-table entry when `lift_resource_any` moves an `own` into the host's table. Run it on release. A `ResourceAny` made from a typed handle keeps running none.

## Acceptance criteria
- [ ] Two interfaces register one host identity with two destructors. A handle lifted through each and released with `ResourceAny::resource_drop` runs its own interface's destructor, once, on both targets.
- [ ] A guest's drop and a host's release of handles from one interface run the same destructor.
- [ ] `lint` passes, and `tests all` is green on both targets with the conformance summary unchanged.
