## What to build
Add two entries to `LinkerInstance` in `src/linker/linker_instance.rs`, named as Wasmtime names them: `func_wrap_concurrent<Params, Ret, F, Fut>(name, func)` where `F: Fn(&Accessor<T>, Params) -> Fut + Send + Sync + 'static` and `Fut: Future<Output = Result<Ret>>`, and `func_new_concurrent<F, Fut>(name, ty: FunctionType, func)` where `F: Fn(&Accessor<T>, Vec<Val>) -> Fut + Send + Sync + 'static` and `Fut: Future<Output = Result<Vec<Val>>>`. The typed entry derives the function type from the closure's types as `func_wrap` does. The untyped entry takes the type at registration as `func_new` does, rather than passing it to the closure as Wasmtime does; the polyfill checks the type at link time and the closure gains nothing from it. The untyped entry takes owned values in and owned values out, where Wasmtime lends slices, because the future outlives the trampoline's frame: it lives in the store as a host task, so nothing it borrows from the call survives. The future's bound is the host future bound of PDD018 (`HostFuture` in `src/concurrency/host_future.rs`): `Send + 'static` natively and `'static` alone in the browser, so a JavaScript promise wrapped as a future satisfies the browser bound. Extend `HostFunc` in `src/linker/host_func.rs`, or add a second registration kind beside it, so a registration records whether it is synchronous or concurrent and carries the body that produces the future; `InstanceRegistration` keeps its shape, and the concurrent kind is what the link rule and the trampoline read. The doc on each entry states that the accessor is a token, that the future runs as a host task the store polls, and that a result vector of the wrong length fails the call.

## Acceptance criteria
- [ ] Both entries compile against the documented bounds on both targets, and a closure that returns an `async` block which awaits and then reaches the host data through `accessor.with` is accepted by the typed entry.
- [ ] A registration through either entry records the concurrent kind, and the derived or declared `FunctionType` is the one the resolver sees, proved by unit tests on the registration.
- [ ] `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.
