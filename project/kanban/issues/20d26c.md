## What to build
Tracing for the polyfill, the runtime layer, and the demo, with the spans visible in the browser's performance panel.

- `tracing` is an ordinary dependency of the polyfill and the runtime layer crates. Nothing records until an application installs a subscriber. Coarse spans are at DEBUG; hot paths are at TRACE.
- Spans on the polyfill's critical paths: component parse, validation, and compile; link and instantiate; `Func::call` and `call_concurrent`; the `run_concurrent` driver and its task turns; host function calls; the canonical ABI's lift and lower and stream and future copies (TRACE).
- Spans in each runtime layer backend: core module compile, instantiate, and call, and the web backend's suspensions.
- The demo installs a subscriber on the page and in the service worker: `tracing-web`'s performance layer, so spans show as marks and measures in the performance panel, and its console writer for events. Spans on the Zena compile, element render and diff, route handling, and IndexedDB.

The owner chose to implement this before a PDD and to write the PDD afterwards.

## Acceptance criteria
- [ ] The polyfill, the runtime layer crates, and the demo depend on `tracing` through `[workspace.dependencies]`.
- [ ] The critical paths above carry spans at the agreed levels.
- [ ] The demo's page and service worker show the spans in Chrome's performance panel as user timing marks and measures, and write events to the console.
- [ ] The demo keeps the performance timeline's buffer from growing without bound.
- [ ] A test proves that a span reaches a subscriber from at least one path in the polyfill.
- [ ] `tests all` and `lint` are green.
