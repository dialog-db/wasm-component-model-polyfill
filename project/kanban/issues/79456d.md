## What to build
Run guest threads through the stack-switching provider.

- The scheduler starts each thread entry (a task's core function, a callback, a thread's start function) through the provider's start, inside the switch module's entry wrapper, and reads the entry's results from the host side at once whether or not it suspended on the way.
- Each blocking built-in reaches the guest as its shim (`src/executor/instantiate.rs`, `src/executor/trampoline.rs`). The shim tries the built-in, returns at once when it is ready, and otherwise suspends. The scheduler resumes the thread when its readiness condition holds, in the order PDD018 fixes, and the finish part computes the result.
- A trampoline starts a thread as a nested start through the provider's start, on a stack of its own above the trampoline. When the new thread suspends or finishes, the start returns to the trampoline, which continues. For an asynchronous lower it returns `STARTED` or `RETURNED` to the caller. This is the reference's `thread.resume` from inside `canon_lower`. The stackful lift's implicit thread and the switches of the thread built-ins go through the provider the same way.
- The provider stays in the store for the whole of a suspension, and nothing takes it out. Today `suspend_with_provider` takes it out of its slot for the length of the call (`src/concurrency/suspend_seam.rs`); that goes. A provider never runs turns inside a suspension, and no readiness condition runs guest code, so a suspension and a nested turn never meet.
- A driver whose store goes idle while a thread is suspended fails with the deadlock cause of PDD018, and `run_concurrent` returns pending in that state. The seam's budget applies to nested turns only.
- A store that drops drops its suspended threads without resuming them. No destructor runs.

## Acceptance criteria
- [ ] A repository test starts a stackful export of one component that calls a second component through a fused adapter, suspends in the second, resumes, and returns. It passes natively on the x86_64 Linux host.
- [ ] A repository test starts a thread by nested start from inside a host trampoline, suspends it, lets the trampoline return, and resumes the thread after its starter. It passes natively on the x86_64 Linux host.
- [ ] A synchronous export lowers a host `async` function whose future is pending for two polls. With the provider, the export returns the host function's result. With the provider turned off through `EngineConfig`, the call fails with the stack-switch cause. A repository test proves both, and runs in the ordinary lanes.
- [ ] A repository test blocks a thread on a host task whose body runs guest work through its accessor. The thread resumes after a turn polls the body, no nested turn runs, and the provider stays in the store for the whole suspension.
- [ ] A repository test drops a store while a thread of a stackful export is suspended. The drop completes, no destructor runs, and a later store on the same engine runs the same export to its end.
- [ ] `lint` passes and `tests all` is green in all four states. A directive that starts passing under a provider leaves the shared list. A line that still fails without a provider sits in `expected-failures.no-provider.txt` with the stack-switch reason. Every line whose reason this card changes is refreshed from a live run.


## Notes from earlier cards
- From the review of 5e6c63: Wasmtime (49, and the 50.0.0-dev reference) never frees a continuation before its store drops (`store.rs` `allocate_continuation`), and each `cont.new` maps a 2 MiB stack. If every thread start does one `cont.new`, a long-lived store's memory grows without bound. Decide how this card bounds that (for example reusing finished continuations' slots is not possible in Wasmtime, so reuse the continuation itself, or document and test the limit), and record the cost in the vendored PATCHES.md.
- Also from that review: the provider keys threads by `ThreadId.index()` and ignores the generation (`stack_switching_provider.rs:190,206`); sixteen expected-failure reasons and the `StackSwitchNeeded` message (`error.rs:914`) still say there is no provider, which becomes false once threads run through it.
