## What to build
Revise `Accessor` in `src/concurrency/accessor.rs` so it carries no store and no lifetime: `Accessor<T>` holds the store's `StoreId` and nothing else. The store owns one slot per thread, a thread-local natively and one static cell in the browser under one declaration, which holds a pointer to the store's context only while a poll is running. Around each poll of a host task's body (`HostTask::poll` in `src/concurrency/host_task.rs`, called from a turn and from `start_host_task`) and around each poll of the `run_concurrent` closure (`StoreContext::run_concurrent` in `src/store/store_context.rs`), the store places its context in the slot and takes it out again before the poll returns; outside a poll the slot is empty. `Accessor::with` takes the slot's contents, fails with the new `SchedulerCause::StoreNotInPoll` when no poll of its store is running or the slot holds another store's id, runs the body against the store, and puts the store back. A `with` inside `with` finds the slot empty inside a poll and fails with the recursive-driver cause, as today, so the slot has to tell an empty slot inside a poll from one outside any poll (record the id of the store in a poll beside the pointer, or track the nesting). Every rule of PDD018 stays: a body reaches the store only inside `with`, and a value taken from the host data must be cloned out. Everything `HostCall` offers a synchronous host function reaches a host task's body through `with` on the `StoreContext`: the host data and `resource_new`. `Store::run_concurrent` hands its closure `&Accessor<T>`, and `HostTaskBody` takes the same reference, so a host task's future holds it across its awaits. The `run_concurrent` entry runs its turns against the store it owns rather than through the accessor, so `attend` and `lend` go with the lent store. One slot suffices because a poll holds the store by `&mut`, so at most one store is inside a poll on a thread. Add the cause to `SchedulerCause` in `src/error.rs` with a message that names the accessor and the poll; Wasmtime panics on the same misuse, and the polyfill returns the error because `with` already returns a result. The visible change is the lifetime leaving the public type; the docs on `Accessor`, `run_concurrent`, and the cause say the accessor is a token.

## Acceptance criteria
- [ ] `Accessor<T>` has no lifetime parameter and `Store::run_concurrent` hands its closure `&Accessor<T>`; a repository test proves `with` reaches the host data during a poll of the closure and returns the body's value.
- [ ] `with` inside `with` fails with the recursive-driver cause, and a nested `run_concurrent` entered from inside `with` still fails with it, each proved by a test.
- [ ] `with` outside any poll, and `with` on an accessor of another store from inside a poll, each fail with the store-not-in-poll cause, proved by tests that pin the message.
- [ ] A host task's future holds the accessor across an await and reaches the host data in a later poll, proved on a host task the test starts through the store.
- [ ] `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.
