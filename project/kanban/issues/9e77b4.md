## What to build
Make the cause of a failed block true when only a frame below the blocked thread can release it. PDD022 adds rule 2 to the order in which the seam names the cause of a block that cannot progress:

1. The cannot-block cause, if a task that must not block is in progress.
2. The stack-switch cause, if a nested start lies between the blocked thread and the base of the real stack.
3. The stack-switch cause, if a host task is pending.
4. The deadlock cause in every other case.

A nested start is a thread that a trampoline starts on a new stack from inside itself. Without a provider the "new stack" is the real stack, above the trampoline: the start intrinsics of PDD020 for an async-typed callee (`src/executor/start_call.rs`, `sync_start_call.rs`, `async_start_call.rs`) run the callee there. The store marks each nested start on its stack of current scopes (`src/concurrency/scope.rs`), and the seam's cause (`suspend_cause` in `src/concurrency/suspend_seam.rs`) reads rule 2 from that mark. The callee's block then fails with the stack-switch cause, because a provider would return control below that point and only the target's capability is missing. Update the seam's documentation and the `Error` / `SchedulerCause` docs: the idle-store rule no longer claims that nothing can meet the condition when a frame below could.

This settles the question bug 347205 asks, with PDD022's answer. Compare with Wasmtime at `v49.0.0-rc.1`, where the same shapes run on fibers and do not fail.

The frame-below directives, which all fail with the stack-switch cause once this lands:
- Component Model corpus: `async-calls-sync.wast:250` and `:251`, `cancel-and-exclusive-lock.wast:196`, `sync-streams.wast:208`.
- Wasmtime corpus: `reenter-during-yield.wast:81`, `stream-zero-ops.wast:201`, `streams-massive-send.wast:238` and `:240`, `sync-streams.wast:186`, `task-builtins.wast:723`, and `trap-if-done.wast` 594, 596, 612, 614, 623, 625, 627.
