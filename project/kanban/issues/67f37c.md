## What to build

Step 5 of the migration (add Wasmi). Add the Wasmi backend to every test lane, so every suite runs on the browser, Wasmi, and Wasmtime backends:

| Suite | Browser | Wasmi | Wasmtime |
| --- | --- | --- | --- |
| `tests native`, `tests web` | Yes | Yes | Yes |
| `tests conformance` | Yes | Yes | Yes |
| `tests zena` | Yes | Yes | Yes |
| The faithfulness suite | Yes | Yes | Yes |
| `bench` | Yes | Yes | Yes |

Each backend has its own list of expected failures in the conformance corpus and in the Zena record. A failure that comes from a missing capability is `Unsupported` with the capability's name. The polyfill's scheduler uses the host-suspension provider on Wasmi.

## Acceptance criteria
- [ ] Each suite in the table runs on the Wasmi backend from a menu command, and `tests all` runs it.
- [ ] The conformance record and the Zena record have Wasmi outcomes, with their own expected failures.
- [ ] A Zena component whose core module uses GC fails on Wasmi at `Component::new` with `Unsupported` that names `gc` or `exceptions`, never with a panic.
- [ ] On Wasmi, a composition of two components translates without the exception barrier and runs.
- [ ] The canonical ABI makes the same number of memory accesses for lists of lengths 1, 100, and 10,000 on Wasmi.
- [ ] No outcome on the browser or Wasmtime lanes moves from pass to fail.
- [ ] `tests all` passes.
