## What to build

The project records where targets, backends and engines differ in many places, each with its own format. Nobody can see them all at once. Build one consolidated view, generated from those sources, so a person can answer "what does not work the same everywhere, why, and which of it we mean to fix".

Sources the view draws from today (the implementor confirms the full list):

- **Conformance expected failures:** `rust/wcmp/tests/corpus/expected-failures.txt`, `expected-failures.web.txt`, `expected-failures.no-provider.txt`.
- **Fidelity expected failures, per backend:** `rust/wcmp-wasm-core-wasmtime/tests/fidelity/expected-failures.txt`, `rust/wcmp-wasm-core-wasmi/tests/fidelity/expected-failures.txt`, and the browser backend's list (card 5ccfd2), including V8 defects and limits the web embedding requires.
- **Fidelity skips and scripts outside every suite:** directives the runner skips (for example `extern.wast:42`, lifted refusals) and scripts no backend runs (for example `data.wast`, `elem.wast`, `global.wast`, which need `extended_const`).
- **Contract allowances:** the browser trap fixture's `AMBIGUOUS` allowance (`rust/wcmp-wasm-core-web/tests/contract.rs`), and contract cases that return early where a backend lacks a capability.
- **Declared capabilities per backend:** what Wasmtime, Wasmi and the browser declare, and what each probe can withhold in a given browser (Safari lacks `multi_memory`, for example).
- **Trap and error mapping gaps:** engine messages that cover several trap kinds and read as `Other` (V8 truncation, SpiderMonkey "index out of bounds", JavaScriptCore "Out of bounds memory access" and signature mismatch).
- **Documented backend limits:** the Wasmi memory64 grow defect, the 64-level host re-entry bound on Wasmi, suspension cases a backend cannot fill, and any similar note in crate docs.
- **The Zena record:** `rust/wcmp/tests/zena/record.txt` (Browser, Native and Wasmtime columns).

For each entry the view shows the target or backend or engine it affects, the kind (engine defect, embedding limit, missing capability, backend limit, not yet implemented), its citation, and whether it is earmarked to be fixed, with the card that covers it where one exists.

The sources stay the single source of truth. The view is derived from them, never edited by hand, and a check fails when it is stale, the way the conformance baseline table does. Where the view lives (a generated markdown document, a menu command that prints it, or both) is for the implementor to propose.

## Acceptance criteria
- [ ] One generated view lists every entry from every source above, grouped so browser-specific, runtime-specific and earmarked-to-fix entries are easy to find.
- [ ] Each entry shows what it affects, its kind, its citation, and the card that covers it, if any.
- [ ] A menu command produces the view, and a `lint` check fails when the committed view is stale.
- [ ] An entry with no kind or no citation fails the check, so a new asymmetry cannot enter without one.
- [ ] `tests all` and `lint` pass.
