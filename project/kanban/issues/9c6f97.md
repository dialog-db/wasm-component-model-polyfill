## What to build

The switch (7eb780, landed `faf3e8510`) changed a behaviour the design fixes and the spec supports. In the browser, dropping a driver's future while a resumed thread is in flight now poisons the store: the next call fails with `Error::Scheduler(SchedulerCause::ThreadAbandoned)` (`rust/wcmp/src/concurrency/host_suspension_provider.rs:233`). The switch rewrote the test that held the old rule: `it_takes_the_stop_of_a_resume_whose_driver_was_dropped_on_the_next_call` (at `afc71435f`) became `it_fails_the_next_call_with_the_trap_of_a_thread_whose_driver_was_dropped` (`rust/wcmp/src/baseline/provider_threads.rs`).

Restore the rule and the original test expectation. The owner ruled (2026-09-30) that the test's expectation must not change while PDD018 agrees with the spec, and it does:

- **PDD018** ("Concurrency Runtime Model", the driver rules): "Dropping a driver's future cancels nothing. The task stays in the store and runs in the next turn of any driver. This is Wasmtime's rule for `call_concurrent`."
- **Component Model spec** (WebAssembly/component-model@e5ee0af, `design/mvp/CanonicalABI.md`, "Embedding" and the `FuncInst` calling convention, lines 582-589 and 806-906): a callee that blocks keeps executing in its own `Thread`; the only way a caller ends a call early is the `OnCancel` callback, which *cooperatively requests* that the callee hurry up; waiting threads resume from `Store.tick`. Nothing in the embedding lets a host's loss of interest trap the callee; the spec traps only through `trap_if` on guest misuse.
- **Wasmtime** (bytecodealliance/wasmtime@cb091c33c, `crates/wasmtime/src/runtime/component/concurrent.rs:6112-6131`, `TaskId::host_future_dropped`): when the host future of a task is dropped after its parameters were lowered, the task is marked dropped and deleted only when all its threads are done; running or suspended threads go on, "and can be resumed by other tasks for this component". No trap.

The 7eb780 reviewer named the fix: the browser backend lets the next borrow of the store re-adopt a revoked flight (a flight whose waiting future was dropped), so the thread's stop is taken by the next driver's turn, as it is natively.

## Acceptance criteria
- [ ] Dropping a driver's future mid-flight in the browser cancels nothing: the thread runs on and its stop is taken by the next driver, on every backend that declares `host_suspension`.
- [ ] `it_takes_the_stop_of_a_resume_whose_driver_was_dropped_on_the_next_call` is restored with its original expectation and passes in the web lanes and on Wasmi.
- [ ] `SchedulerCause::ThreadAbandoned` is removed, or kept only for a case the spec supports, with the citation in its doc.
- [ ] No soundness guarantee from edf2c7 (a forgotten flight's host function cannot reach its store) is weakened.
- [ ] `tests all` and `lint` pass.
