## What to build

A host task gets its own waker from its first poll.

`StoreContext::start_async_host_task` (`rust/wcmp/src/store/store_context.rs`)
polls a host task's body the first time with the waker of the running turn
(`active_waker()`). Every later poll comes from a turn that takes the task's own
waker from the host task set. `begin_blocking_host_task` does the same. `Future`
allows a poll to change the waker, but a future that keeps the waker of its
first poll then wakes a waker that no longer leads back to the task. Its task
is never polled again.

The `wasi:webgpu` spike (`~/Git/github.com/cdata/wasi-webgpu-test`) met this in
`wasi-webgpu-wasmtime`. Its `on-submitted-work-done` waits on wgpu-core's
callback through `callback-future` 0.1.0, which clones the waker of its first
poll only. The call never resolved on the polyfill. A host future that keeps
the waker of its latest poll resolved at once. The spike's unit test
`it_shows_that_callback_future_wakes_the_waker_of_its_first_poll_only`
(`rust/spike-webgpu/src/work_done.rs`) shows the crate's behavior.

Make the task's own waker exist before the first poll, and use it there, so
that every poll of a host task has one waker.

## Acceptance criteria
- [ ] A host future that keeps the waker of its first poll and wakes it later
      resolves its call, on both targets, through an asynchronous lower and
      through a blocking one.
- [ ] A host future that changes nothing about wakers behaves as before: the
      concurrency tests pass unchanged.
- [ ] `lint` passes, and `tests all` is green on both targets with the
      conformance summary unchanged.
