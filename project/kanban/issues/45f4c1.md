## What to build

From the independent review of fa9643 (landed with this card's parent). The runtime layer now returns `Error::Backend` instead of panicking when the browser refuses a store (a host function of a forgotten flight reaching its own store past its caller). But the top-level `wcmp` crate still routes its id and handle tables through `inner.data()` (`rust/wcmp/src/store/store.rs:318-330`, `store_context.rs:126`), so a host reaching its `wcmp::Store` in that state still panics. Find whether that state is reachable through the `wcmp` API; if it is, route those tables so every fallible `wcmp` operation returns a structured error.

Also extend the runtime layer's refusal sweep test (`rust/wcmp-wasm-core-web/tests/web.rs`) with a handle-carrying `Val` and a non-empty import list, so the `extern_in_store` and `value_in_store` branches are exercised.

## Acceptance criteria
- [x] A `wcmp`-level host in the refused state gets a structured error from every fallible operation, or the card shows the state is unreachable through `wcmp`.
- [x] The sweep covers handle-carrying values and imports.
- [ ] `tests all` and `lint` pass.

## Review notes
- 2026-10-07 delivered (host session, backlog-burndown-001-q3).
  - Reachable: yes, with safe code. A host forgets a call's future after
    its first poll resumed the thread, keeps the `wcmp::Store` in a
    `thread_local`, and a host function of that thread reaches it. The
    existing `it_frees_a_store_a_host_function_drops_while_the_thread_that_called_it_runs`
    already does this.
  - Fix: the runtime layer gains `try_data` (`BackendStore`, `Store`,
    `StoreContextMut`; the browser `Owner` answers `None` where it
    refuses). `wcmp` keeps the store id beside the core store, and asks
    `reachable()` first in every fallible entry: `Store::resource_new`,
    `resource_drop`, `run_concurrent`, `lock_tables`; `StoreContext::resource_new`,
    `lock_tables` (which the stream and future ends go through) and
    `enter_guest`; `Func::call`/`TypedFunc::call`, `start_concurrent`,
    `Linker::instantiate`, `Module::instantiate` (through `enter_guest`), the
    driver (at its start and every poll), and `Source::read`. These fail
    with the new `Error::StoreRefused` (recorded with `api update`). Only
    the infallible `data`, `data_mut`, `hostcall_fuel` and `set_hostcall_fuel`
    panic there, and their docs now say so.
    `CoreInstance::get_export` no longer panics (cached id).
  - Tests: `it_refuses_every_fallible_operation_of_a_store_a_host_function_reaches_past_its_context`
    (web; 10 operations, each `StoreRefused`; the refused `resource_drop`
    leaves the handle live). The runtime-layer sweep gained an
    instantiation with an import, and `Global::new`, `Table::new`,
    `Table::set` and `Table::grow` with a `funcref` handle, plus a
    `try_data`/`try_data_mut` check.
  - Owner decision: the new public variant `Error::StoreRefused`. Wasmtime
    has no such state, so there is no name to copy.
  - Gate: native 1694/1694, web 1675/1675, `lint clippy clippy-wasm32
    rustfmt public-api doctests` green. `tests all` and full `lint` run on
    the composed series tip.
- 2026-10-07 context-free review: a refused `StreamReader`/`FutureReader` close used to drop the
  reader's end before the gate refused it. `close_readable_end` now asks
  `reachable()` first, and the sweep closes a reader in the refused state. It
  then shows that a later close still releases the stream's record.
