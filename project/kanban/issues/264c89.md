## What to build
The `web` and `native` subjects. A cross-target test (PDD004's cross-target attribute) runs each compiled scenario through the polyfill in the browser and natively, and reports a stage and error text per subject.

- Read the compiled scenario components and the Wasmtime observations from the build. They must reach the browser lane as well as the native lane.
- For each scenario: `Component::new`, the polyfill's `Linker`, instantiation, and each call through `Func::call` with `Val` arguments. Capture output lines for comparison.
- Judge each subject with the scenario model: against the Wasmtime observations when the Wasmtime run passed, else against the expectations file.
- Scenarios are found on their own. Adding one needs no Rust code in the runner.
- The suspend provider stays on, which is the default.
- Report the stages in a form the record and the gate can read next. This card does not add the record or the gate.

Notes from the review of 17e40b (landed as `4d3706559`):
- The pinned Zena prints through p3 `wasi:cli/stdout@0.3.0`, not p2 stdio as PDD024's Facts section says (confirmed with `wasm-tools component wit` on the compiled printer). The Wasmtime run links both p2 and p3 WASI and captures standard output in one in-memory pipe. The polyfill's test host must provide p3 standard output too.
- The Wasmtime run's fixed test interface is `wcmp:scenario/host` with `echo: func(text: string) -> string`.
- Typed calls fail in the Wasmtime run with 'does not make typed calls yet' until ff3743.

## Acceptance criteria
- [x] Scenario 1 runs under `web` and `native`, and each subject reports a stage and its error text.
- [x] A test changes one result in the observations of a passing scenario. The `web` and `native` subjects each report `mismatch`. If no Zena scenario passes on a subject yet, say so on the card and name the subject the test covers.
- [x] `tests native debug` and `tests web debug` pass.
- [x] `lint` passes.
