## What to build
Bring the Zena toolchain into the build as a flake input, and compile each scenario's Zena programs at test time.

- Add a `zena` flake input for `github:elematic/zena`, locked at `b2237f7e65847eda43ef1f4094eea77fe225ce0d`, the revision PDD024 read. The input does **not** follow this flake's `nixpkgs`: Zena builds against its own. The lock gains a second `nixpkgs`.
- Use Zena's `zena` package without change, and only its `zena` command. The package never enters the development shell.
- A Nix build step finds each scenario under one directory and compiles its Zena programs with `zena build --target component`, adding `--wit` and `--world` when the scenario has a WIT world. A contributor writes no Nix or Rust code per scenario.
- The build never fails because Zena refused a program. It keeps Zena's exit status and error output as a build product, so a later step can record the `compile` stage.

## Review notes
### Round 1 (`review-f3f4c8-3a2fcc00`, tip `214c25fad`): needs-changes

> VERDICT: needs-changes (small). All six acceptance criteria are met in substance, but two assertions in the new check are rubber stamps, and the report claims more than they prove.
>
> BLOCKING:
> (1) flake.nix:295-297 + tests/zena/build-check/declared-world: the declared-world case does not show that --wit/--world is passed. I compiled declared.zena with the pinned zena WITHOUT --wit: exit 0, and the component is byte-identical (cmp) to the one built with --wit wit --world declared, and identical to scalar.wasm. Deleting the world_args branch at build.sh:44-46 leaves zena-scenario-build green. Fix: use a program that compiles only with its world (e.g. it imports a function the world declares), or add a negative case whose world declares an export the program lacks and assert a refusal naming the world.
>
> NON-BLOCKING:
> (2) flake.nix:299: 'test zena-revision = ${zenaRevision}' compares zena.rev with itself, so it can never fail. The report says it checks against the lock; it does not. Compare with (builtins.fromJSON (readFile ./flake.lock)).nodes.zena.locked.rev.
> (3) flake.nix:236: zenaRevision = zena.rev has no fallback. With --override-input zena path:<copy>, evaluating zena-scenarios fails with 'error: attribute rev missing' (verified). The dev shell and packages.zena still evaluate, but lint cannot run against a local Zena checkout. A loud failure fits PDD024's pin gate, but a clear throw or dirtyRev handling would help.
> (4) build.sh:36: the glob has no nullglob. A scenarios dir with no subdirectories (e.g. only a README) fails the build: cd into the literal '*/' fails and a stray $out/* is created (verified). A scenario directory with no .zena files yields an empty output dir silently (verified); a later record step should flag it.
> (5) build.sh:47-49: any nonzero exit counts as a refusal. A missing or crashed toolchain gives status 127 and is recorded like a refusal (verified with ZENA=/nonexistent). This matches PDD024's 'build never fails' rule and is unreachable under Nix, but a later compile-stage classifier should know it.
> (6) The --world <program stem> rule: PDD024 says only that a scenario has 'an optional WIT world' read through --wit/--world, and that 'one WIT world is the contract' for an integration pair. It neither supports nor contradicts the stem rule. The rule is a workable reading, since an importer and an exporter need different worlds in one package. Its risk: a misnamed program gives Zena's error '--world X is not a world the --wit document declares', exit 1, which PDD024's 'Moving the Pin' section would attribute to Zena. The owner should ratify the rule in the PDD.
> (7) The log path-stripping at build.sh:50 is untested: the grep at flake.nix:293 is unanchored and would also match an absolute path. Anchor it with ^refused.zena.

The reviewer ran `lint` and `tests all` on the tip: all green. Finding 6 (the `--world <program stem>` rule) is a design question for the owner: PDD024 neither supports nor contradicts it.
