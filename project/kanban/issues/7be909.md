## What to build
Close the browser gap in the poisoned-store discard. Card b6a68d discards every queued guest work item and drops every host future when a trap poisons the store, but under JSPI in the browser `run_driver_turn` (`src/store/store_context.rs:421` at the time of that card) runs the store's deferred work before any poisoned check: it takes the next thread, enters a switched thread, and steps switchers and plans. `Scheduler::discard_all_work` leaves that deferred work alone (a resume already issued, a failed start handed over later, the next thread, switchers, plans). So a later driver in the browser can resume a guest thread after the trap. PDD023 says a poisoned store runs no guest code and lists no target differences. That card's review traced the path in code without reproducing it, and its implementor judged a poisoned check before the deferred work unsafe because plans and resumed JSPI stacks would be left busy; the `discard_all_work` and poison docs state the gap.

Reproduce the case with a browser test first. Then make a poisoned store refuse to resume guest code from deferred work while it still releases every JSPI stack and plan it holds, so nothing is left busy. Remove the gap from the docs.

## Acceptance criteria
- [x] A web test shows a guest thread that is parked or switched at the moment of a trap, and a later driver of the poisoned store that does not resume it; the test fails without the fix, or the review notes say why the case cannot occur.
- [x] No JSPI stack or plan is left busy after the poison; a later host-only `run_concurrent` still returns.
- [x] The docs of `discard_all_work` and the poison no longer state a browser gap.
- [x] `lint` passes and `tests all` is green on both targets, any directive that starts passing has its line removed from the expected-failure list, and every line whose reason this card changes is refreshed from a live run.


## Review notes
- 2026-09-27T06:04:17Z (from the b6a68d round-2 review) Also correct the public `Store` rustdoc (`src/store/store.rs:55` and `:71-83` at `a0b47e4bb`), which says without qualification that a thread ready to resume is discarded and that a poisoned store runs no more guest code.
- 2026-10-05 (host session, backlog-burndown-001-q2) Reproduced with `baseline::provider_threads::it_resumes_no_thread_that_yielded_before_a_trap_in_a_later_driver_of_the_poisoned_store`: a synchronous export yields to a started thread that traps, which leaves the export's thread as a parked switcher. Without the fix a later host-only `run_concurrent` fails with `CannotEnter` as its first turn takes the switcher back. That happens on the web lane and natively too (stack-switching and Wasmi host-suspension), so the gap was never browser-only. Fix: in a poisoned store `step_deferred_work` awaits only the stop of a thread already in flight (nothing can call it back), then `release_deferred_work` drops the deferred start (new `abandon_start` on the provider), the next thread, the switchers and every plan (marks ended, scopes cut) without starting or resuming a thread. Error cascades to plan owners inside the trapping turn are unchanged. Docs of `discard_all_work`, `poison` and the public `Store` rustdoc updated. No plan-left-after-poison fixture: the release path is shared, but only the switcher case is pinned by a test.
- 2026-10-06 Composed gate on the q2 series tip: `tests all` green on every lane (native/web debug and release, both no-provider lanes, Wasmi, fidelity, Zena, demo) with no unexpected or stale corpus line, `tests regenerate --dry-run` proposes no list change, and `lint` green.
