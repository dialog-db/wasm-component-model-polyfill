## What to build
`tests/corpus/expected-failures.txt` holds one line per directive the polyfill does not pass, as `<path>:<line> <category> <reason>`, and the harness fails when a listed directive passes or an unlisted one fails. When a change alters the failure text of many directives, the list must be regenerated, and today that is a hand-rolled loop: an implementor working card `929c8f` blanked the list, ran `tests native debug --no-fail-fast -E 'binary(conformance)'`, and merged the printed `unexpected:` lines back by hand to refresh 175 reasons while keeping each line's category and hand-written parenthetical. That procedure is not reproducible and is easy to get subtly wrong: the same hand loop on card `741912` stripped 28 hand-written annotations from lines that card never touched, and only a reviewer reading the diff caught it. Add a menu verb under `tests` (for example `tests regenerate`) that runs the conformance harness natively in a mode that prints the current reason for every failing directive, and rewrites `expected-failures.txt` from the run: a line whose directive still fails keeps its category and any parenthetical and takes the new reason; a directive that now passes loses its line; a newly failing directive gets a line with a placeholder category the harness rejects until a person fills it in. The reviewer of card `45740e` asked for the same thing from the other side: the harness compares an expectation by file and line only (`tests/conformance.rs:885-902`), so a stale reason is invisible to every gate, and no command prints the live reason for a listed directive. The regeneration mode is that command; a dry-run flag that prints the diff without writing the list covers the reviewer's case. Make the harness support this through an environment variable or an argument rather than by editing the list, and document the verb in `tests/corpus/README.md` next to the description of the list. Decide with the design corpus whether `expected-failures.web.txt` is regenerated the same way or left to hand edits, and say so in the README.

## Acceptance criteria
- [ ] A menu verb regenerates `expected-failures.txt` from a native run, preserving categories and parentheticals, dropping lines that pass, and adding placeholder lines for new failures.
- [ ] Running the verb on an unchanged tree leaves the list byte-identical, proved by running it and diffing.
- [ ] `tests/corpus/README.md` documents the verb and the web list's treatment; `markdown format` has run.
- [ ] `lint` passes and `tests all` is green on both targets.
