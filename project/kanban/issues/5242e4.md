## What to build
Write the PDD for host resource destructors that are asynchronous, and settle the README's "Asynchronous destructors" row.

**What the sources say.**
- **The spec.** At the pinned spec revision (`component-model-src` `a53b241`, 2026-09-15), `canon resource.drop` has no `async` form. The destructor runs as a synchronous cross-component call, and "destructors may not block" (CanonicalABI.md, `canon_resource_drop`). A destructor may spawn an explicit thread that blocks.
- **The README.** Its row says the polyfill "accepts `resource.drop async`, but the destructor runs synchronously". That looks stale: the pinned Wasmtime 49 translator handles only `ResourceDrop` (`crates/environ/src/component/translate.rs`). Verify it and correct the row either way.
- **Wasmtime.** Host resources can have asynchronous destructors through `LinkerInstance::resource_async` and `LinkerInstance::resource_concurrent`, the latter taking an `Accessor` (`crates/wasmtime/src/runtime/component/linker.rs`). Its own TODO notes that `resource_concurrent` holds the store exclusively until the destructor completes, so guest code does not run meanwhile.
- **The polyfill.** It has only synchronous host destructors (`HostResource::new`). A WASI host needs asynchronous ones, for example to flush or close a stream when a guest drops it.

This design builds on PDD023's cancellation and poisoned store, so it follows the close of that thread.

The PDD must settle these questions:

1. **API.** Mirror `resource_async` and `resource_concurrent`, or state each difference and its reason.
2. **Scheduling.** Decide whether a host destructor that is pending blocks the dropping guest thread, runs beside it, or holds the store as Wasmtime does. Reconcile this with the spec rule that destructors may not block, with and without a suspend provider.
3. **Failure.** Say what happens when a host destructor fails or is still pending when the store is poisoned or dropped.
4. **Guest destructors.** Confirm that guest destructors stay synchronous, as the spec requires, and cover the explicit-thread pattern the spec allows.
5. **The README row.** Say what the feature table states afterwards.

The PDD follows `project/design/README.md`: plain English, the six sections, Goals and Non-goals that express scope, and Test Cases that a later card can lift as acceptance criteria. Do not name later PDDs.

## Acceptance criteria
- [ ] The PDD is formatted with `markdown format` and passes the `markdown` flake check.
- [ ] It answers questions 1 to 5, each with its reason and a citation to the spec or Wasmtime.
- [ ] Its Test Cases cover:
  - a host async destructor completing after a guest drop on both targets
  - a failing host destructor
  - a pending destructor when the store is poisoned
  - a guest destructor that spawns a blocking thread
- [ ] The owner accepts the PDD before any implementation card is filed.
