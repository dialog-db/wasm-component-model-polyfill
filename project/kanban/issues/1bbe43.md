## What to build
Close the findings the review of card f3a070 left open.

1. **A host error context from another store.** `ErrorContextId` is a per-store index and generation with no store identity, so the host lower has no wrong-store check. Lowering an `ErrorContext` or `Val::ErrorContext` from store A into store B either silently hands the guest a handle to B's record with the same identity, which carries a different message, or, when B has no such record, fails as `Error::internal` (`src/concurrency/task_tables.rs:1270` at the landing) and poisons B. PDD023 says a value from another store fails with the wrong-store cause and does not poison. Wasmtime does not check either, and `StreamAny` documents the same gap (`stream_any.rs:48-52`). Either add a store identity and fail with the wrong-store cause before any state changes, or, if the owner accepts Wasmtime's gap, state in `error_context_any.rs` that the misuse is undetected and make a missing record fail with a structured cause rather than an internal error.
2. **Tests for the paths the removed refusal used to guard.** Host import parameters and results carrying an error context (`trampoline.rs:662`, `:906`), host stream and future `error-context` payloads (`host_copy.rs:202`, `source.rs:144`), repeated lowers of one host-held value, and the `ErrorContext`-specific mistyped lift and lower branches (`component_value.rs:633`, `:643`).

## Acceptance criteria

## Review notes
- 2026-10-08 delivered (host session, backlog-burndown-001-q4), commit
  `fix(error-context): Refuse an error context from another store`.
  - Item 1: followed PDD023 (wrong-store cause, no poison), not Wasmtime's gap.
    `ErrorContextAny` and `ErrorContext` carry the `StoreId` of the store that
    lifted them. `Func::call` and `call_concurrent` refuse a value from
    another store with `InstantiationError::WrongStore` before the call
    creates its task: untyped at any depth (list, option, map, record,
    variant, result, tuple), typed in `ErrorContext`, `Vec`, `[T; N]`,
    `HashMap`, `Option` and parameter tuples. The refusal comes before
    anything changes, so the store is not poisoned (`CallValues::check_store`,
    and hidden `ComponentValue::check_store` and
    `ComponentParameters::check_store` for typed values). A host's own
    `ComponentValue` type cannot override the hidden check (`StoreId` is not
    public), so an error context inside one fails only at its lower, inside
    the call, which poisons; the `ErrorContext` and `check_store` docs say so.
    A lower made inside
    a running call can only fail: argument lowering runs inside the task, where
    a failure is a trap. `lower_error_context` checks too, so a host function
    result, or a host stream or future write, of another store's value fails
    the guest's call or built-in with the same cause, as any host failure
    there does. Wasmtime checks neither (the review's citation, `values.rs`
    `ErrorContextAny(u32)` at v49.0.0-rc.1).
  - Tests (`src/baseline/error_context_transfer.rs`, both targets): another
    store's value is refused untyped and typed, alone and after a value of
    this store in a list, where both stores mint the same identity, with no
    count changed and the store usable after; one held value lowered three
    times, each a handle of its own; an untyped and a typed host function that
    take an error context and return one (new `RELAY` component); held values
    written into a guest's stream and future; a host consumer reading a guest's
    `stream<error-context>`; `ErrorContext` `lift_flat`, `load` and
    `lower_flat` declared as `u32` refused with `HostValueMismatch` before the
