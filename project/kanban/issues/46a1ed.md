## What to build
**Needs the owner's decision on PDD023 first.** PDD023's `subtask.cancel` pseudocode (around its lines 257 and 272) has an asynchronous cancel give way once whenever the callee has not resolved, whether or not the cancel woke anything, and says it follows the reference's `canon_subtask_cancel`. The reference has since dropped that give-way: component-model #723 (commit `07afb81`, 2026-09-16) removed the `else: thread.yield_()`, so the current `definitions.py` (`:2396-2400`) returns `BLOCKED` without yielding, and `request_cancellation` (`:474-475`) resumes only a cancellable, ready implicit thread. Wasmtime 49 also yields only on its wake paths (`concurrent.rs:4283-4330` at `v49.0.0-rc.1`). So the current reference and Wasmtime agree: an asynchronous cancel that wakes nothing answers `BLOCKED` at once.

The polyfill follows PDD023 as written (cards 727b97 and 45ccc2). The visible difference: when the callee is ready but not woken, the ready callee runs in the give-way and the cancel can answer a terminal state (for example 4) where the reference and Wasmtime answer `BLOCKED`.

If the owner revises PDD023 to the current reference: remove the unconditional give-way from an asynchronous `subtask.cancel` so it gives way only when the cancel woke a thread; update the tests that rely on the give-way (`tests/baseline_cancel.rs`, `tests/baseline_cancellable.rs`); refresh any corpus line that changes from a live run.

Also consider, from the 45ccc2 review: the polyfill checks `set_has_pending_event` when the cancel runs (`task_tables.rs:1545-1547`), while Wasmtime clears `wake_on_cancel` permanently for the first waiter when an event arrives (`concurrent.rs:5393-5400`). They differ when two threads wait cancellably on one set (Wasmtime still wakes the second) and when the event leaves the set before the waiter runs (the polyfill admits it again). `take_held_callback_of` (`scheduler.rs:1210`) may have an analogue for held callbacks (unverified).
