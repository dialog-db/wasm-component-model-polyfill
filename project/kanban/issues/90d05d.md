## What to build
The third feature: `stream<T>` and `future<T>`. Design the readable and writable ends in the per-instance handle table, the `stream.*` and `future.*` built-ins (`new`, `read`, `write`, `cancel-read`, `cancel-write`, `drop-readable`, `drop-writable`), the readiness and partial-copy rules, the copy of element payloads between two components' memories through the lift and lower seam the runtime model fixed, transfer of an end between components (`StreamTransfer`, `FutureTransfer`), and lifting and lowering of `stream<T>` and `future<T>` as values in parameters and results. On the host side, the Rust types a host uses to read from and write to a guest's stream or future, on both targets, mirroring Wasmtime's names where one exists.

After this phase the WASI 0.3 HTTP handler fixture (card 657c60) is expected to run; say so in the Test Cases and name the built-ins it still needs, if any.

An input from the checkup of 2026-09-21: payloads of hundreds of megabytes, and more, are an expected use of this polyfill, so the copy budget the design sets at Wasmtime's 128 MiB default must be configurable through `EngineConfig` or such copies fail by design. The element-count bound on the untyped `Val` list path (card `d0d703`) is a separate number for a separate cost and the design should not conflate the two.

Name the corpus files this phase owns (for example `sync-streams.wast`, `cancel-stream.wast`, `partial-stream-copies.wast`, `closed-stream.wast`, `drop-stream.wast`, `cross-task-future.wast`, `future-completion-order.wast`, `futures-must-write.wast`, `zero-length.wast`, `same-component-stream-future.wast`, `validate-no-stream-char.wast`) and any that stay deferred with the reason.
