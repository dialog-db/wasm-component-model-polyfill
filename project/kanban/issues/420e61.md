## What to build

Add a section to the root `README.md` that compares the polyfill's backends, so a person choosing one knows its limits before they hit them. Today that knowledge is spread over card notes, crate docs, expected-failure lists and records.

For the browser backend, the Wasmi backend and the Wasmtime backend (the control), state:

- **Capabilities declared**, per the lexicon (`multi_memory`, `memory64`, `tail_call`, `exceptions`, `function_references`, `gc`, `relaxed_simd`, `threads`, `stack_switching`, `host_suspension`), and for the browser which ones depend on the engine's probes (Safari lacks `multi_memory`, for example, and takes the slower memory path).
- **Host suspension**: how each provides it (JSPI; Wasmi's resumable calls; none on the Wasmtime backend today) and its known limits (a first-stretch trap inside a host function reaches only an awaiting caller in the browser; Wasmi finishes a flight inside the poll that starts it).
- **Memory**: mapped or allocated (Wasmi zero-fills every grown page), the browser's 4 GiB limit on memory64 offsets from 32-bit code, and the copy paths.
- **Performance**: the web per-call cost of the host-suspension path (card 721eac) and the f64-as-BigInt carrier, with numbers from the bench.
- **Fidelity**: conformance, fidelity and Zena results per backend, with the date and the source record, for example Wasmi 2349/2440 conformance and 2/14 Zena against 2409/2440 and 14/14 on Wasmtime.
- **Known limits by kind**: engine defects (cited), limits the web embedding requires (cited to the JS API), missing capabilities, and backend limits (the Wasmi 64-level re-entry bound and its memory64 grow defect).

Keep the numbers traceable: each figure names the record or bench it comes from. When the consolidated asymmetry view (card 86f861) exists, link to it for the full list, and keep this section a summary.
