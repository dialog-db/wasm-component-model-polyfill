## What to build
Nothing about the polyfill's speed has been measured. The canonical ABI lowers a value one field at a time through runtime-layer memory writes, which in the browser is a JavaScript boundary crossing per write, and the untyped `Val` path allocates per value. Before any of that is optimized, the project needs a benchmark suite, and the suite must let one benchmark definition run on both targets and produce numbers a person can compare across them.

The constraint is the target split. `criterion` and `cargo bench` run natively only; `wasm-bindgen-test` runs in the browser but is a test runner, not a benchmark harness, and prints nothing for a passing test. Pick or build a small harness the workspace owns: one `#[wcmp_macros::bench]`-style attribute (or a plain function signature) that a benchmark author writes once, a runner that on native drives it with a wall-clock timer and on the web drives it with `performance.now()` inside headless Chromium through the same WebDriver plumbing the tests use, warm-up and iteration control that are the same on both targets, and a report of the same shape from both: name, iterations, median and spread, bytes or elements per iteration where the benchmark states them. The report is written as JSON under `$CARGO_TARGET_DIR/bench/` per target, like the conformance summary, and a `bench native|web` menu command builds and runs the suite as a Nix derivation.

The first benchmarks, written once and run on both targets: a `u32` call with no memory traffic (the floor); a string round trip at a few sizes; a `list<u32>` and a `list<record>` round trip at a few sizes; a resource handle passed and dropped; a call through a `wac` composition (adapter and transcoder cost); and `Component::new` for the smoke test's guests. Each names the guest it drives and the value it moves so the number has a meaning.

Absolute times differ between a native engine and a browser; the point of one definition is a like-for-like shape on both targets, so that a change's effect can be read on each and the ratio between them can be watched. State that in the README of the suite, with how to read the numbers and what is not comparable.

## Acceptance criteria
- [ ] One benchmark definition compiles and runs unchanged on native and on `wasm32-unknown-unknown` in headless Chromium.
- [ ] `bench native` and `bench web` menu commands run the suite as Nix derivations and write a JSON report of the same shape per target.
- [ ] The first benchmarks listed above are in the suite with a stated guest and payload each.
- [ ] The suite's README explains how to read the numbers and what is not comparable across targets.
- [ ] `nix flake check` builds the suite for both targets (running it stays a menu command).
