## What to build
Accept the stackful form of `canon lift async` (no `callback` option) and run it. The translator refuses it today (`src/executor/translate.rs:474-487` and `:902-909`). Accept it on every target behind the existing gate `wasm_component_model_async_stackful`, which stays off by default. With the gate off the component fails with `Error::Unsupported`, as now.

A stackful export's core function runs as the task's implicit thread. It returns nothing, delivers its result through `task.return`, and blocks inside built-ins as it needs. The rules are those of the reference (`canon_lift` in `definitions.py`):

- The task passes the entry gate of PDD018. It does not take the exclusive thread of its instance, because only a sync lift or a callback lift needs it.
- The core function receives the flat parameters under the limit of the asynchronous lift. A stackful lift of a sync-typed function stays invalid.
- When the core function returns, the implicit thread ends. If the task has no other thread and has not resolved, the call fails with Wasmtime's message "async-lifted export failed to produce a result", as a structured cause of `wcmp::Error`.
- `task.return` resolves the task, as for a callback export. Work the task does after it resolves stays in the store, as PDD019 states.

No provider exists yet, so the implicit thread starts as a direct call and a block takes the nested turn. A stackful export that never blocks behaves the same on every target. A block that only a frame below can release fails with the stack-switch cause.

The corpus lines this feature owns: `stackful.wast`, `drop-waitable-set-stackful.wast`, `task-deletion.wast`, `task-return-traps.wast` 93, 106, 121, 138 (Wasmtime corpus); `big-interleaving-test.wast` 912, 973, 1295, 1508, 1623, 1640, 1651, `sync-barges-in.wast:323`, `values/variants.wast:186` (Component Model corpus). Those that pass without a provider leave the list here. The rest keep a stack-switch reason until a provider serves them.
