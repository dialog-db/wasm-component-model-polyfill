## What to build
Write the PDD for interrupting guests and bounding the resources they use. A host that runs untrusted components, such as a browser plugin host or an in-browser tool that runs user programs, must be able to stop a guest that runs too long and cap what it allocates. Today the polyfill offers neither. A guest that loops forever freezes the browser tab, because it runs on the page's main thread. The only budget today is the copy budget per call (`Store::set_hostcall_fuel`).

**Reference.** Wasmtime offers fuel (`Store::set_fuel`, `Config::consume_fuel`), epoch interruption (`Store::epoch_deadline_trap` and related), and a resource limiter (`Store::limiter`, `ResourceLimiter`) (`crates/wasmtime/src/runtime/store.rs`).

This design builds on the hooks the runtime-layer PDD (f259d6) leaves for it, so it is blocked on that card.

The PDD must settle these questions:

1. **Interruption natively.** Map fuel and epoch deadlines onto the Wasmtime backend, and say what a host sees when one trips: a trap cause, or a yield back to the scheduler, as Wasmtime's async yield-on-epoch does.
2. **Interruption in the browser.** The browser has no fuel or epochs. Weigh the options with evidence: running the store in a Web Worker the page can terminate, instrumenting core modules with fuel counters at compile time, JSPI-based yields at instrumented points, or a combination. For each, give its cost in code size and speed, and what the page can recover after it fires. State what "the same behavior on both targets" can mean here.
3. **Web Worker hosting.** Decide whether running a `Store` inside a Worker is a supported configuration, with JSPI and asynchronous compilation there, and how host functions that need the page reach it. Card f3f685 notes that the tree has no Worker today.
4. **Limits.** Cover a limiter for memory and table growth, and the store's live-record cap (2170bc), on both targets, with a structured error when a limit is hit.
5. **Interaction with the scheduler and the poisoned store.** Say which interruptions poison the store, as a trap does under PDD023, and which only suspend a task.

The PDD follows `project/design/README.md`: plain English, the six sections, Goals and Non-goals that express scope, and Test Cases that a later card can lift as acceptance criteria. Do not name later PDDs.

## Acceptance criteria
- [ ] The PDD is formatted with `markdown format` and passes the `markdown` flake check.
- [ ] It answers questions 1 to 5, each with its reason and, where it follows Wasmtime, a citation. Browser claims cite the platform specification or engine documentation.
- [ ] Its Test Cases cover:
  - a guest in an infinite loop stopped on both targets, with the host still responsive in the browser
  - a memory growth past a limit refused with a structured error on both targets
  - the store's state after each kind of interruption
- [ ] The owner accepts the PDD before any implementation card is filed.
