## What to build
Write the PDD for host binding generation. Today a host of the polyfill writes `Val` trees or typed tuples by hand against `func_wrap` and `TypedFunc`; nothing is generated from WIT. Wasmtime embedders instead keep the WIT package in `wit/`, call `wasmtime::component::bindgen!`, and get a `Host` trait per imported interface, an `add_to_linker` per interface, a typed struct per world with `instantiate` and one method per export, Rust types with `ComponentType`, `Lift`, and `Lower` derived for every WIT record, variant, enum, and flags, and `Resource<T>` for resources. The compatibility outlook (PDD003) lists a `bindgen!` equivalent as "Implement".

The goal of the design is workflow parity. A host author writes the same code they would write for Wasmtime: the same `wit/` layout, the same macro name and invocation forms (`bindgen!()`, `bindgen!("world")`, `bindgen!(in "path")`, `bindgen!({ world, path or inline, with, ownership, trappable_error_type, imports/exports flags, require_store_data_send })`), the same generated names (`Host` traits, `add_to_linker`, the world struct, `instantiate`), and the same `Resource<T>` shape. The macro does the platform-specific work.

The PDD must settle these questions:

1. **What the macro emits on each target.** The proposed shape is: on native, the polyfill's macro is a re-export of Wasmtime's; in the browser, it is the polyfill's own macro with the same signature, emitting code against the polyfill's API. The PDD must reconcile this with the recorded substrate decision: the polyfill's `Engine`, `Store`, `Linker`, and `Instance` are polyfill-owned types over `wasm_runtime_layer` on every target, and Wasmtime's macro emits code that names `wasmtime::component::Linker<T>`, `wasmtime::Store<T>`, and Wasmtime's `Lift`/`Lower` traits. Either the native macro is also the polyfill's own (one generator, two targets, identical output shape) and parity is with Wasmtime's source-level workflow rather than a literal re-export, or the native build of the polyfill exposes Wasmtime's component types directly, which revisits that decision. State the choice and its reasons. The state of wasm_runtime_layer's own component-level ambitions is relevant input.
2. **Whether to fork Wasmtime's generator or write one.** `wasmtime-wit-bindgen` (the generator behind the macro, over `wit-parser`) emits `wasmtime::component` paths and depends on Wasmtime's derive machinery; it is not reusable as is and tracks Wasmtime's release train. Weigh a fork retargeted to the polyfill against a generator of our own that reads the same WIT with `wit-parser` and emits against the polyfill's API. `wit-parser` was removed from the runtime crate on purpose; a compile-time dependency of the macro crate only does not reverse that. State how the generator keeps up with Wasmtime's option set over time.
3. **The derive.** Generated bindings need `ComponentType`, `Lift`, and `Lower` (or the polyfill's equivalents) for user-defined Rust types, so a record can be passed as a Rust struct and a variant as a Rust enum, through `TypedFunc` and `func_wrap`. Today only the `ComponentValue` tuple family exists. The PDD states the derive's contract against the type system (structural equality with the export's declared type, the `TypeMismatch` positions) and its relation to the existing `ComponentValue` trait.
4. **Resources.** How `Resource<T>` maps onto `ResourceHandle` and `ResourceTypeId`, how `with` maps a WIT resource to an existing host type, and how the derive treats `own<T>` and `borrow<T>` fields.
5. **Errors and results.** `trappable_error_type`, `wasmtime::Result` versus the polyfill's `Result`, and how a host error from a generated `Host` method reaches the guest.
6. **What is out of scope now.** The async flags (`imports: { async }`, `exports`, concurrent host methods) belong with the concurrency features. State that the generated shape must not block them.

The PDD follows `project/design/README.md`: plain English, the six sections, Goals and Non-goals expressing scope, test cases that a later card can lift as acceptance criteria. Do not name later PDDs. Two PDDs are acceptable if the derive stands on its own: one for the derive and the typed value contract, one for the macro; if so, file this card's follow-up for the second.

## Acceptance criteria
- [ ] The PDD is formatted with `markdown format` and passes the `markdown` flake check.
- [ ] It states the native and browser macro strategy and reconciles it with the polyfill-owned-types decision, with reasons.
- [ ] It lists the macro invocation forms and options it commits to matching Wasmtime on, and those it defers, one line each.
- [ ] It states the derive contract for user-defined Rust types and how it relates to `ComponentValue`.
- [ ] Its Test Cases cover: the same host source compiling and running natively and in the browser; a record and a variant crossing the boundary as Rust types; a resource through `Resource<T>`; a host error from a generated method reaching the guest as a trap; a `with` mapping to an existing type.
- [ ] The owner accepts the PDD before any implementation card is filed.
