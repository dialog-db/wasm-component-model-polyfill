## What to build
Every fixture under `tests/corpus/fixtures/` is a core module written in WAT and wrapped with `wasm-tools component embed` and `wasm-tools component new`. Nothing built by a language toolchain, with the binding layer a real guest carries (`cabi_realloc` from an allocator, wit-bindgen's lift and lower code, a `wasi:` world's imports), has run through the polyfill. The value-type and resource coverage the suite claims is proven only against hand-written guests.

Add fixtures built by a real toolchain from non-trivial WIT, regenerated by `fixtures/build.sh` under the flake's pinned tools so the outputs stay byte for byte reproducible, and run by the conformance harness like the rest. Two fixtures, each with its sources checked in next to the binary:

1. **A synchronous guest against a rich world.** A Rust guest built with `cargo component` (or `wit-bindgen` plus `wasm-tools`) whose WIT uses records, variants, enums, flags, options, results, nested lists, strings, and a guest-defined resource with a constructor, methods, and a destructor, and which imports a host interface with the same shapes. Its `assertions.wast` calls every export and checks every value and every destructor. This fixture must pass on both targets when the card lands. If a second language toolchain is cheap to pin (a C guest through `wasi-sdk`, or Python through `componentize-py`), add one guest from it too, because a second binding layer catches ABI assumptions the first does not.

2. **A WASI 0.3 HTTP handler.** A guest that implements `wasi:http` as released with WASI 0.3, where the handler's body and trailers are `stream<u8>` and `future<T>` and the export is `async`. Build it with the same toolchain against the 0.3 WIT packages, and write assertions that instantiate it and call the handler with a request. Today the polyfill rejects `async` functions, so this fixture's directives enter `expected-failures.txt` as `deferred-feature` with the exact reason, and the fixture's job until then is to hold the target: it states in one place what a real 0.3 guest needs from the polyfill (the async lift form, the stream and future built-ins, `error-context`, the task built-ins) and it flips to passing as those land. Do not gate this card on any of them.

The build must run inside `fixtures` under Nix: pin `cargo component` or `wit-bindgen`, the `wasm32-wasip2` (or the wasip3-era) target of the flake's Rust toolchain, and the WASI 0.3 WIT packages at a named version, and record the exact commands in `build.sh` as for the existing fixtures. Both fixtures also join the smoke test (`rust/wcmp-smoke`) as steps where they pass, so a person sees a real-toolchain guest run natively and in the page.

## Acceptance criteria
- [ ] `fixtures` rebuilds both fixtures reproducibly from checked-in sources with tools pinned in the flake, and `fixtures/README.md` documents them.
- [ ] The synchronous rich-world fixture passes every assertion in the native and web lanes, and the smoke test runs it on both targets.
- [ ] The WASI 0.3 HTTP handler fixture is in the corpus with its directives listed in `expected-failures.txt` as `deferred-feature`, one line per reason, and the list stays accurate as features land.
- [ ] Any failure the rich-world fixture exposes in the polyfill is filed as its own card and linked from this one.
- [ ] `tests all` passes on both targets.
