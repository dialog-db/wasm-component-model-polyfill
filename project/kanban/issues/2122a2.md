## What to build
From round 2 of the review of card 674450 (landed as `3fd7a6ac6`), finding 1, plausible and not memory-unsafe. `Stop::Failed` is recorded only on the rejection microtask (`watch()` in `src/concurrency/jspi_provider.rs`). If a resumed thread traps or fails and the store drops in a microtask that runs before that rejection handler (for example an application task woken by a host import the thread called before trapping), `retain_if_resuming` (`jspi_provider.rs:413-417`) still sees "resuming with no stop", marks and retains the store, but the stack has already unwound and no try part runs, so the store and its host data never drop. A related case: a host import the resumed thread calls drops the store's owner, and the thread then finishes without another blocking built-in; the store also leaks.

Let the watch handler, or a release hook kept with the thread records, free an orphaned store once the thread's stack has settled.

Test gaps from the same review: a store dropped after the resumed thread stopped but before `poll_stop` frees at once; a guest `try_table`/`catch_all` around a shim cannot catch the dropped-store trap.

## Acceptance criteria
- [ ] A store dropped after its resumed thread failed but before the rejection handler ran is freed once the handler runs; a web test proves it.
- [ ] A store whose owner a host import drops during a resume, with no further blocking built-in, is freed; a web test proves it.
- [ ] The two test gaps above are covered.
- [ ] `tests all` and `lint` are green.
