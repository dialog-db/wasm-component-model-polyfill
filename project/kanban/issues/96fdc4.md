## What to build
Make `error-context` a value type that crosses between components. Today the type projection refuses it (`src/component/project.rs:216`).

- It flattens to one `i32` and takes four bytes in memory with an alignment of four.
- It appears anywhere a value appears: a parameter or a result; inside a record, a tuple, a variant, an option, a result, or a list; and as the payload of a stream or a future, through PDD021's boundary context.
- A lift reads the handle from the source instance and fails with "handle is not an error-context" when the handle is of another kind. A lift does not remove the source handle: an error context is copied between components, not moved.
- A lower adds a handle to the destination instance and adds one to the record's count.
- A count past `u32::MAX` fails with Wasmtime's "reference count overflow" (`futures_and_streams.rs:4558-4589` at `v49.0.0-rc.1`).

Error-context records join the store's record cap: a new record past the cap fails with "resource table has no free keys".

The host surface is the next card of this design.

## Acceptance criteria
- [ ] A repository test on both targets sends an error context to another component in a parameter, in a list, and as the payload of a stream. The destination reads the debug message and drops each handle. The record leaves the store when the last handle drops.
- [ ] A repository test proves the flat and memory layout of `error-context` inside a record and a list, and that a lift of a handle of another kind fails with "handle is not an error-context".
- [ ] A repository test proves that error-context records count toward the record cap.
- [ ] `lint` passes and `tests all` is green on both targets, any directive that starts passing has its line removed from the expected-failure list, and every line whose reason this card changes is refreshed from a live run.
