## What to build

A browser lane that runs the web tests in WebKitGTK, beside headless Chrome.

The web lanes run only in headless Chrome. The owner's webview is WebKitGTK, and
36bcc3 stands in for Safari with a person in Epiphany. The `wasi:webgpu` spike
(`~/Git/github.com/cdata/wasi-webgpu-test`, `harness/`) ran the polyfill in
WebKitGTK 2.54.1 MiniBrowser under Nix, through WebKitWebDriver, on a headless
Weston. What it needed:

- a headless Weston (`--backend=headless`), with its runtime directory under
  `/run/user/<uid>`, because a Wayland socket's path must fit in 108 bytes;
- MiniBrowser from `webkitgtk_6_0`'s `libexec`, and WebKitWebDriver;
- for a dedicated worker with WebGL, the features `AllowWebGLInWorkers` and
  `UseGPUProcessForWebGL`; JSPI and `requestAnimationFrame` work in a worker as
  shipped.

Run the web lanes there, or a chosen subset if the whole is too slow, with the
same pass/fail rules.

## Acceptance criteria
- [x] A menu command runs the web tests in WebKitGTK on a headless Weston, with
      nothing installed by hand.
- [x] CI runs it, or the card records why not.
- [x] Each test that fails only in WebKitGTK is a new card.

## Review notes


- 2026-10-18 (implementer): `tests webkit debug` (Linux) replays the web
  debug archive in WebKitGTK 2.54.1's MiniBrowser on a headless Weston,
  through the stock `wasm-bindgen-test-runner` with `WebKitWebDriver`
  handed over as its geckodriver (`nix/webkit-tests.sh`). A first version
  ran one browser per test under nextest: about 13 s a test, because the
  runner regenerates the bindings each time, so near four hours for the
  archive. The lane now asks `cargo nextest list` for the tests the
  default profile and any filter select, and runs each wasm32 binary once
  with the rest passed as `--skip`: 1850 tests in 72 binaries in about two
  minutes here. A test that fails in the shared page runs again on a page
  of its own, and only a failure there counts: the Content Security Policy
  tests (a policy stays on a page) and the yield-wake test failed only in
  the shared page. Nothing is installed by hand; the dedicated-worker
  WebGL features the spike needed are not needed by these tests.
- CI does not run it yet: 17 tests fail only in WebKitGTK. They are filed
  by cause rather than one card per test, since each cause is one fix:
  fbbef9 (memory64 is off in JavaScriptCore: 11 tests), 4b5a17
  (JavaScriptCore's trap messages: 3 tests, one covering four traps), and
  1429ec (three tests that assume Chromium). 8601e7, blocked by those
  three, adds the lane to CI and to `tests all`.
- 2026-10-18 (peer review, the card's first): ACCEPT, with eight non-blocking findings,
  answered after the verdict and not reviewed again.
  Answered in the lane's commit: a run that fails and names no failing
  test now fails its binary rather than passing; the runner's timeout,
  which bounds one page and so a whole binary here, is
  `WCMP_WEBKIT_TIMEOUT` (900 s by default); the failed binaries' output is
  kept under `~/.cache/wcmp-tests/webkit-logs`, which outlives the
  workspace; the parallel runs use `$BASH`, and each binary's skip list
  goes through a file of its own rather than an xargs line; the cleanup
  kills and waits for Weston on exit, and an interrupt exits through it;
  this note's count of 4b5a17's tests is corrected. Recorded here:
  - The lane covers the web debug archive with the default profile, the
    tests `tests web debug` runs. The conformance corpus without a
    provider runs with `tests webkit debug --profile no-provider`, since
    the arguments reach `cargo nextest list`. The release archive is not
    wired: a release build changes the polyfill's code and not what the
    browser's engine does.
  - For the owner: the 17 WebKit-only tests are filed as three cards by
    cause, not one card per test (acceptance criterion 3). Each card lists
