## What to build
In the conformance harness (`tests/conformance.rs`, around line 178), `ModuleDefinition` inserts a definition into `self.definitions` only when the definition succeeds, so a `(component definition $A ...)` that fails to translate leaves an earlier `$A` bound. A later directive that names `$A` then runs against the wrong component and can pass or fail for the wrong reason. Reviewer of the prepared-call card found eight directives of `wasmtime/async/exceptions.wast` (143-146, 215-218) passing against section 1's component because sections 2 and 3 define `$A` again and fail on the asynchronous start; the six byte-identical web substrate messages corroborate it. Remove the stale binding before compiling a definition, so a failed definition leaves no definition of that name, then rerun the harness on both targets and refresh `expected-failures.txt`, `expected-failures.web.txt`, and the README baseline table from the live output.

## Acceptance criteria
- [ ] A failed `component definition` leaves its name unbound; a unit test of the harness proves a directive that names it afterwards fails with no definition rather than running an earlier component.
- [ ] The eight `exceptions.wast` directives report their true outcome, and the expected-failure lists and the README baseline table match the harness on both targets.
- [ ] `lint` passes and `tests all` is green on both targets.
