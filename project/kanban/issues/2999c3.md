## What to build
From the review of card 923a21 (landed as `e7c8a1df8`). A task now lives until its last thread ends, so an explicit thread routinely runs after its task's host call returned. A trap in such a thread goes to a failure channel nobody reads: `fail_export_task` (`src/store/store_context.rs:1646-1680`) fills the task's channel, which is never detached after the call returns (`src/func.rs:451`). The trap is swallowed and guest code keeps running. PDD019 says a late trap fails the next driver; the reference and Wasmtime trap there too. The corpus shows the symptom at `during-sync-call-no-sibling-resume.wast:156` ("unknown handle index 2" after X's cannot-block trap ends its task).

Also from that review: a NoResult from `run_thread` on the no-provider switch path returns to the switching thread's built-in even when the ended thread belongs to another task (`src/executor/thread_builtins.rs:330`), unlike the provider path, which fills that task's channel. Make both paths report the failure the same way.

Missing tests named by the reviewer: a sync-lift export whose explicit thread runs and ends after the return; a guest-to-guest caller (subtask release on NoResult; `subtask.drop` before or after the last thread ends); a thread that suspends in the provider after the implicit exit, then resumes and ends last; the no-provider `run_thread` path; a late trap of a post-return thread; a sync lift that exits owing a borrow with explicit threads.

## Acceptance criteria
- [ ] A trap in an explicit thread that runs after its task's host call returned fails the next driver, as PDD019 states; a test proves it on both targets.
- [ ] A NoResult from the last thread ending is reported to that thread's own task on both the provider and the no-provider switch paths.
- [ ] The missing tests above exist and pass.
- [ ] `tests all` and `lint` are green.
