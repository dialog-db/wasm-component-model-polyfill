## What to build
In the browser a yield returns control to the host executor through one `setTimeout` of zero per yield (`src/concurrency/yield_wake.rs:78-104`), which PDD018 chose so that a guest spinning on `thread.yield` or `waitable-set.poll` does not starve the page. The HTML timer initialisation steps clamp a timeout nested more than five deep to at least 4 ms, and every major browser throttles timers in a background tab to about once a second, so a callback export that yields per event runs at most a few hundred events a second in the foreground and about one a second in a background tab; Safari applies both. A `MessageChannel` post is a macrotask with neither clamp, which keeps the rule the design asked for (network responses and timers already queued run before the guest's next item) without the floor. Replace the timeout with a port message and keep the timeout as the fallback for a global without `MessageChannel`; the `landed` flag keeps its meaning. Record the numbers with the benchmark suite when it exists; this card does not wait for it.

## Acceptance criteria
- [ ] A web test stubs the global's `setTimeout` to fail the test if the wake ever uses it while `MessageChannel` exists, and yields a few hundred times under a generous sanity bound stated in the test; the timing bound is a sanity check, not the evidence.
- [ ] The fallback still wakes the driver when `MessageChannel` is absent, proved by a test with a stubbed global or by a recorded manual check.
- [ ] PDD018's wording of the wake after a yield is corrected if it names the mechanism; `markdown format` has run.
- [ ] `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.
