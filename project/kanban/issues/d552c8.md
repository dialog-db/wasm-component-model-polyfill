## What to build
Add the store's host tasks: the future one call of a host `async` function produces, which the scheduler owns and polls. Define one trait for the future's bound whose definition differs per target, `Send` natively so `Store<T>` stays `Send` as it is today, and no bound in the browser, where a JavaScript promise wrapped as a future is not `Send` and awaiting one is the purpose of a browser host function; host code then compiles on both targets without change. The future is `'static`, does not borrow the store, and reaches the host data only through the accessor of the `run_concurrent` card. Implement the scheduler side of the contract as a store operation the later asynchronous lower calls: poll the future once with the waker of the active turn, or a waker that does nothing when no turn is active; if ready, lower the result at once through the boundary context of the subtask and report `RETURNED` with no subtask; if pending, add the future to the store's host tasks, insert a subtask entry in the caller's handle table in the `started` state, and report `STARTED` with that index, the state in the low four bits and the index above them. A host task that joined the store since the last turn counts as woken, and the next turn polls it with the driver's waker so no wake is lost. When the future completes in a later turn, queue a lowering item that lowers its result through the subtask's boundary context, moves the subtask to `returned`, and fills its pending event with a subtask event. Through a synchronous lower the call succeeds if the first poll resolves the future or if the suspend seam is filled; otherwise the operation fails with the stack-switch cause. The registration entry point for a host `async` function and the asynchronous lower itself are out of scope, so no guest reaches this path yet. A synchronous host function called through an asynchronous lower returns `RETURNED` at once; that path keeps its behavior.

## Acceptance criteria
- [ ] The bound trait compiles a `Send` future on the native target and a non-`Send` future (a `wasm-bindgen-futures` `JsFuture`) in the browser from one source, proved by a test per target.
- [ ] `Store<T>` is still `Send` on the native target, proved by a compile-time assertion.
- [ ] A test starts a host task whose future is ready on the first poll and sees the result lowered at once, `RETURNED`, and no subtask entry.
- [ ] A test starts a host task whose future is pending, sees a subtask entry in the `started` state and a `STARTED` status carrying its index, and after the future completes in a later turn sees the subtask `returned`, a subtask event in its pending slot, and the result lowered.
- [ ] A test starts a host task with no turn active and shows the next turn polls it with the driver's waker.
- [ ] A test through a synchronous lower with a pending future and no suspend provider fails with the stack-switch cause.
- [ ] The tests run on both targets.
