## What to build

Step 1 of the migration (build beside). Memory access in the browser backend, through a generated accessor module.

Rust on `wasm32` addresses only memory 0 of the polyfill's own instance, and a guest memory is another `WebAssembly.Memory`. So the browser cannot lend guest bytes to Rust.

- **Scalars.** A generated accessor module imports the guest memory and exports the scalar loads and stores. The backend puts those exports in the function table of the polyfill's own instance, and Rust calls them through a function pointer: WebAssembly to WebAssembly, with no JavaScript frame. The requirement is the absence of a JavaScript frame; this card proves the mechanism.
- **Bulk copies.** `read`, `write`, `with_bytes`, and `Memory::copy` need two memories in one module. Where the browser declares `multi_memory`, the accessor module imports both and a bulk copy is one `memory.copy`. Where it does not, a bulk copy is one call of JavaScript `TypedArray.set`. A bulk copy crosses into JavaScript at most once.
- **`with_bytes`.** Copies the range into a buffer of the polyfill once and lends that buffer. The meaning is the same as on native backends; only the cost differs.
- **Shared memory.** Copies use atomic access, and a shared memory is never lent as a slice. A page makes a shared memory without cross-origin isolation, so no special headers are needed.
- **Bounds.** Every method checks its range; a range outside the memory is a structured error.

## Acceptance criteria
- [ ] `with_bytes` on an unshared memory returns the bytes of the range; on a shared memory it returns a copy.
- [ ] A range outside the memory is a structured error for every memory method.
- [ ] A test shows that a scalar load runs with no JavaScript frame on the stack.
- [ ] A bulk copy is one `memory.copy` when `multi_memory` is declared, and one `TypedArray.set` when a test forces it off.
- [ ] The shared contract tests for memory pass in the web lane.
- [ ] `lint` and `tests web debug` pass.
