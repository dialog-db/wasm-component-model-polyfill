## What to build

A host that bounds the memory of a guest needs to know how much memory the
guest holds. Sapling, a host of the polyfill, lowers the maximum of each memory
of a component to 64 MiB before it compiles the component. When a store traps,
Sapling must tell whether a core memory of the instance had grown to that cap.
If one had, the store fails with the reason `memory` in place of `trap`.

The polyfill gives a component `Instance` only `get_func`, `get_module`, and
`exports`, so a host cannot read a core memory. Add a read of the current size
of each core memory of an instance, in the style of Wasmtime's `Memory`: the
size in pages through `size`, and in bytes through `data_size`. The read runs no
guest code, so it works after a trap poisons the store.

Wasmtime's component `Instance` has no such read. Its nearest API is for
debuggers: `Store::debug_all_instances` and `Instance::debug_memory`
(`crates/wasmtime/src/runtime/debug.rs` at `v50.0.0`). Both need
`Config::guest_debug`.

## Owner's decision (2026-11-20)

The owner chose to add a read of the size of each core memory of an instance to
the polyfill, on the Wasmtime backend and in the browser, in the style of
Wasmtime's API. Sapling counts a memory "at the cap" when its size equals the
cap.

### The API

- `Instance::core_memories(&self) -> &[Memory]` lists the memories.
- `Memory` is a new public type, `Clone` and `Copy`, as `wasmtime::Memory` is.
  `Memory::size(&self, &Store<T>) -> Result<u64>` gives the size in pages.
  `Memory::data_size(&self, &Store<T>) -> Result<usize>` gives it in bytes.
  These are the names and units of `wasmtime::Memory::size` and `data_size`.
- The list holds each memory that a core instance of the component defines and
  exports, at any depth of nesting, in the order of instantiation. A memory
  that one instance imports and exports again is listed once, under the
  instance that defines it. A module instantiated twice gives two memories. A
  core module that the host supplies counts too.
- The reader of the shape of a core module records the first export name of
  each memory that the module defines. The instantiation reads each one by
  that name after it makes the core instance. A read checks the store, then
  asks the runtime layer for the size in bytes, so it works on every backend
  and runs no guest code.

### Where the API differs from Wasmtime

`notes/differences-from-wasmtime.md` records these too.

- Wasmtime's component `Instance` has no list of memories. Its nearest API is
  for debuggers: `Store::debug_all_instances` and `Instance::debug_memory`
  (`crates/wasmtime/src/runtime/debug.rs` at `v50.0.0`), behind
  `Config::guest_debug`.
- A memory that its module defines and does not export is not listed. The
  browser reaches only the exports of an instance, and Wasmtime reaches other
  memories only through guest debugging.
- `Memory` gives the size and nothing else: no `page_size`, `ty`, `data`,
  `read`, `write`, or `grow`.
- The reads take `&Store<T>` and return a `Result`, as `CoreInstance::get_export`
  and `CoreExtern::ty` take the store. Another store fails with
  `InstantiationError::WrongStore`. Wasmtime takes `impl AsContext` and panics.

### Choices for the owner

- The names. `Memory` has no `Core` prefix, as `Module` has none, because no
  component-level type has that name. Wasmtime has no name for the list, so
  `core_memories` is new.
- Whether `Memory` also gives `page_size`, or the maximum through `ty`. The
  runtime layer has only pages of 64 KiB.

### Tests

`rust/wcmp/tests/baseline_core_memories.rs` has five tests: the list across
each kind of memory, a growth, a read after a trap, a module that the host
supplies, and a read through another store. In the test of the trap, the guest
grows its memory to the maximum of 4 pages, a grow fails, and the guest traps.
The next call fails with the cannot-enter cause, and the size reads 4 pages.
