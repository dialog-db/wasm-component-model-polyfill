## What to build
Split every blocking built-in into a try part and a finish part, as the reference's thread model does (`Thread.wait_until` in `definitions.py`). No provider exists yet, so the nested turn of PDD020 still serves every block. What a guest observes does not change.

- The try part runs in the host trampoline. It sets up the wait: it records the thread's readiness condition in the store and returns. If the condition already holds, the built-in is ready.
- The finish part computes the built-in's result and writes what the built-in writes to guest memory, such as the event of `waitable-set.wait`.
- A readiness condition only reads the store. It changes nothing, never polls a host future, and never runs guest code, as the reference's `ready_func`. The scheduler evaluates the conditions between items and resumes a waiting thread in the order PDD018 fixes for threads that became ready together.

The built-ins that block today reach `SuspendSeam::suspend` and `SuspendSeam::give_way` (`src/concurrency/suspend_seam.rs`): `waitable-set.wait`, the synchronous stream and future copies and cancels, the synchronous start intrinsic, `thread.yield`, and the synchronous lower of a host `async` function.

A synchronous lower of a host `async` function parks its future in the store as a host task, in every case. Turns poll it with the driver's waker, as they poll every host task, and the lowering of its result makes the waiting thread ready. With this rule the store always knows about a pending host future. This retires `SuspendSeam::while_blocked_on_a_call_future` and its mark (`src/store/store_context.rs:662`, `src/concurrency/scheduler.rs:2646`). Rule 3 of the failed-block cause (a pending host task gives the stack-switch cause) now reads the store's host tasks. Retire the two obligations `src/concurrency/suspend_provider.rs` places on the first provider, since this card meets them.
