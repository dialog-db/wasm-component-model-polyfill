## What to build
Twelve corpus lines fail because the runtime layer has no exception tag type and no GC reference types: `cm/linking/tags.wast` (4), `wasmtime/tags.wast` (1), `wasmtime/exceptions.wast` (1), and six `wasmtime/alias-region-*.wast` and `wasmtime/modules.wast` lines that use `(ref i31)` or concrete function references. Wasmtime supports both. Both browsers and Wasmtime implement the underlying core features (the outlook lists exception handling and GC as shipped everywhere), so parity is possible once `wasm_runtime_layer` carries them: a `Tag` extern kind, and reference-typed values beyond `funcref` and `externref`. Propose the extension upstream (with the backend issues in 4599cd), carry it in the vendored browser backend and a patched native backend meanwhile if the owner agrees, and lift the polyfill's parser patch that turns tag imports into errors.

Parity: the extension lands in the runtime layer's shared trait; both backends implement it; the corpus lines flip in both lanes.

Blocked in practice on the upstream conversation; file the proposal first and keep this card until the runtime layer exposes the kinds.

## Review notes
Proposal draft for `DouglasDwyer/wasm_runtime_layer` (2026-09-15). The polyfill cannot open the issue itself; the owner posts it and links it here.

**Title:** Exception tags and typed references in the extern and value surface

**What is missing.** `Extern` and `ExternType` know functions, globals, memories, and tables, and `ValType` knows the numeric types plus `funcref` and `externref`. A core module that imports or exports a tag cannot be instantiated: the Wasmtime backend reports "tags are not supported in the wasm_runtime_layer", and the browser backend's parser refuses tag imports and exports. A module whose types name a garbage-collection reference, `(ref i31)` or a concrete function reference, is refused the same way ("ref type (ref i31) is not supported"). Both features are shipped in every browser and in Wasmtime, and a Component Model host meets them as soon as it links real components: the `wasm-tools` adapters for exceptions import a tag, and shared-everything linking passes typed function references.

**Proposal.**
1. A `Tag` extern: `Extern::Tag(Tag)`, `ExternType::Tag(TagType)` with `TagType::new(params)` and `params()`, `Tag::new(store, TagType)` and `Tag::ty(store)`, and a `backend::WasmTag` trait the backends implement. The Wasmtime backend wraps `wasmtime::Tag`; the browser backend wraps `WebAssembly.Tag`. Modules import and export tags like any other extern, so `Imports::define` and `Instance::get_export` carry them with no new API.
2. Typed references: `RefType` gains the heap types the GC proposal defines, `func`, `extern`, `any`, `eq`, `i31`, `struct`, `array`, `none`, `nofunc`, `noextern`, and a concrete type index, with a nullability flag, and `ValType::Ref(RefType)` replaces the two fixed reference variants (kept as constructors for source compatibility). `Val::Ref` carries an opaque reference the host can only pass through. Module type parsing accepts every reference type wasmparser accepts; a backend that cannot represent one reports it at `Module::new` rather than at instantiation.
3. Exceptions raised by a guest and not caught keep their current shape (an error from the call); catching a guest exception on the host is out of scope for this proposal.

**Why upstream rather than a patch.** The change is to the shared trait, so every backend implements it once; the polyfill carries a patched browser backend already (see `rust/vendor/js_wasm_runtime_layer/PATCHES.md`) and would rather shrink that patch set than grow it.

**What the polyfill does meanwhile.** The twelve corpus directives stay recorded as `substrate` failures. Carrying the extension in the vendored browser backend and in a patched copy of the Wasmtime backend is possible but doubles the patch surface; the owner decides whether to do that before upstream answers.
