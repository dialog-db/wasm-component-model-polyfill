## What to build
Write the PDD for a core-Wasm runtime layer that the project owns and hosts. It replaces the `wasm_runtime_layer` crate and its two backends, evolves with the polyfill, and is shaped for the polyfill's needs, not for a general facade over many engines.

**Why now.** PDD002 made `wasm_runtime_layer` the runtime layer, with "contribute upstream" as the default and "the polyfill does not replace the runtime layer on the web". In practice the polyfill carries growing patch sets instead:

- The browser backend has 13 patches (`rust/vendor/js_wasm_runtime_layer/PATCHES.md`): asynchronous compilation, JSPI, guest threads through JSPI, host entry at any depth, types the layer cannot name, host-error survival, and more.
- The Wasmtime backend has 2 patches (`rust/vendor/wasmtime_runtime_layer/PATCHES.md`): the Wasmtime 49 build and stack switching.
- 71 polyfill source files use the layer's types.

The next needs do not fit the upstream trait either:

- Exception tags and typed or GC references (ff5733).
- Modules with GC-typed globals and tag exports, which every Zena program has (48c67c).
- Asynchronous instantiation of large modules (f16638) and a compile cache per caller (7b77c5).
- Re-entrant host calls (797d67).
- Trap wording that matches across engines (6a02b3).
- Interruption and resource limits, which the layer has no hooks for.

There is also a release blocker. The backends are wired in with `[patch.crates-io]` (`Cargo.toml:82-84`), and Cargo applies `[patch]` only in the root workspace. So a downstream consumer gets the unpatched upstream backends.

The PDD must settle these questions:

1. **Relationship to PDD002.** State the decision this replaces and why: the runtime-layer goal, the "does not replace the runtime layer on the web" rule, and the upstream-first default for this crate. Say what stays true, for example that no layer type appears in the polyfill's public API, and that attribution and licenses carry forward from the MIT/Apache-2.0 upstream. Decide whether PDD002 gets revised or the new PDD supersedes its runtime-layer sections.
2. **Shape.** Choose a trait with pluggable backends, as upstream has, or concrete types chosen per target. Only two backends are required: Wasmtime natively and the browser's `WebAssembly` API. State whether other engines stay possible and at what cost.
3. **Type surface.** Cover the full set of core value and reference types: the GC heap types, typed function references, `exnref`, tags as externs, and shared memory as a non-goal or not. Decide which references the host can only pass through and which it can inspect, given that JavaScript cannot read the fields of a Wasm GC object. A module must never be refused only because the layer cannot name one of its internal or unused items.
4. **Asynchrony and suspension.** Asynchronous compilation and instantiation are first-class on every target. The suspend providers (stack switching natively, JSPI in the browser) are part of the layer's design, not patches over it.
5. **Memory access.** Today every guest memory read in the browser crosses into JavaScript (see `rust/wcmp-bench/README.md`). Design the access model (bulk copies, borrowed views, or both) with the benchmark suite as the measure.
6. **Errors and traps.** Traps get a structured kind that is the same on both targets, so the polyfill's messages do not depend on V8's wording. Host errors survive a guest catch, as patch 4 does today.
7. **Hooks for later features.** Leave room for fuel or epoch interruption and for memory and table limits, even if the PDD does not design them.
8. **Migration.** Move the polyfill over without a big-bang rewrite, with the conformance summary unchanged at every step, and retire `rust/vendor/`. List which existing cards the new layer makes obsolete (candidates: ff5733, f16638, 7b77c5, 797d67, 4599cd, 6a02b3) and which it only makes easier.
9. **Publication.** The layer and the polyfill can be published and used downstream without `[patch]`. State the Wasmtime version policy, which today is a pin on `=49.0.0-rc.1`.

Non-goals to consider: a general-purpose facade for engines the polyfill does not use, and implementing any Wasm Core proposal inside the layer. The engines still supply core features.

The PDD follows `project/design/README.md`: plain English, the six sections, Goals and Non-goals that express scope, and Test Cases that a later card can lift as acceptance criteria. Do not name later PDDs. Engineering planning decides crate names and directory structure.

Design input from the PDD024 session (2026-09-28), measured on scenario 5's component built by the pinned Zena (`b2237f7`) and read with `wasm-tools print`:
- Two core modules export the tag `__zena_exception`; the GC-typed globals (`(mut (ref null N))`) are internal definitions, neither imported nor exported.
- The component shell aliases only `realloc`, `memory` and the export functions from its core instances. It never aliases the tag or a GC global.
- So the current backends refuse these modules for constructs that never cross the component boundary: the browser backend while converting every global's type into the layer's `funcref`/`externref`-only model, the native backend at the tag export. The new layer should accept a core module whose tags and reference-typed globals the component does not use, without needing to model their values. An uncaught Zena exception still has to become a trap (in the browser it surfaces as a JavaScript `WebAssembly.Exception`).
- `tests zena` measures the result: today every Zena scenario except scalar-export stops at `parse` in the browser, and every one with strings, console, async or exceptions stops at `parse` natively.

## Acceptance criteria
- [ ] The PDD is formatted with `markdown format` and passes the `markdown` flake check.
- [ ] It states the relationship to PDD002, with reasons, and the corpus reads consistently afterwards (PDD002 revised or explicitly superseded where it conflicts).
- [ ] It answers questions 2 to 9 above, each with its reason and, where a choice follows Wasmtime or the upstream crate, a citation.
- [ ] Its Test Cases cover:
  - a module with GC-typed globals and an exported tag instantiating on both targets
  - an asynchronous instantiation of a module above the browser's synchronous limit
  - the same trap kind on both targets
  - the polyfill building as a downstream dependency with no `[patch]` section
  - the conformance summary unchanged across the migration
- [ ] It lists the existing cards it makes obsolete or changes.
- [ ] The owner accepts the PDD before any implementation card is filed.
