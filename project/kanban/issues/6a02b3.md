## What to build
Three `substrate` lines in `tests/corpus/expected-failures.web.txt` exist only because V8 words a trap differently from Wasmtime: `wasmtime/async/subtask-wait.wast:82` expects `wasm \`unreachable\` instruction executed` and the browser prints `Guest function threw an error: unreachable`; `cm/async/builtin-trap-poisons-instance.wast:9` and `wasmtime/async/sync-call-context-trap.wast:47` are the same shape, and the older `wasmtime/trap.wast:30` and `wasmtime/big-strings.wast:342,379` lines too. Card 98606b set the precedent: vendored patch 9 in `rust/vendor/js_wasm_runtime_layer` renames a thrown `WebAssembly.Exception` to Wasmtime's `thrown Wasm exception`. Extend that mapping in `JsErrorMsg` (`src/lib.rs`) so a `WebAssembly.RuntimeError` renders as Wasmtime's text for the same trap — at least `unreachable`, out-of-bounds memory and table access, integer divide by zero and overflow, and indirect-call signature mismatch — taking each string from `wasmtime-environ`'s `trap_encoding.rs` at the pinned version. Record the mapping under patch 9 in `PATCHES.md`, remove every web line the mapping makes pass, and refresh the README's browser paragraph from a live run; if the two async rows then agree across targets, the design's "the same counts on both targets" becomes literally true (see the reconciliation docs card).

## Acceptance criteria
- [ ] A web test proves each mapped trap renders with Wasmtime's wording through the polyfill's error chain.
- [ ] The web lines the mapping makes pass leave `expected-failures.web.txt`, and the README's browser paragraph matches a live run on both targets.
- [ ] `PATCHES.md` records the mapping; `lint` passes and `tests all` is green on both targets with no unexpected or stale line.
