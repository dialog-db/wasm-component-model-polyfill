## What to build

Step 5 of the migration (add Wasmi), build beside. Create `wcmp-wasm-core-wasmi`, the Wasmi backend. Wasmi is the practical native backend. It depends on the current major version of Wasmi with a caret requirement. This card covers everything but host suspension.

- Modules, instances, externs, tags, references, host functions, memory access, and trap kinds, as the contract states. Wasmi's `TrapCode` uses Wasmtime's names; each kind carries Wasmtime's message.
- `with_bytes` on an unshared memory lends the memory's own bytes.
- Declare only what Wasmi implements faithfully. Per its README, Wasmi implements tail calls, SIMD, relaxed SIMD, memory64, and multi-memory, and not GC, exception handling, typed function references, or threads.
- Run the shared contract tests and the faithfulness suite on the Wasmi backend. A test that needs a capability Wasmi lacks checks for `Unsupported` with the capability's name instead.

The Wasmi backend builds for `wasm32` too, but no lane runs it in the browser.

## Acceptance criteria
- [ ] The shared contract tests pass on the Wasmi backend, apart from tests that need a capability Wasmi does not declare.
- [ ] A test that needs `gc` or `exceptions` gets `Unsupported` naming the capability, never a panic.
- [ ] The trap fixture reports each kind with the same message as the Wasmtime backend.
- [ ] `with_bytes` on an unshared memory copies nothing.
- [ ] The faithfulness suite passes for Wasm 2.0 and each declared capability, apart from cited expected failures.
- [ ] `cargo package` succeeds for the crate.
- [ ] `lint` and `tests native debug` pass.
