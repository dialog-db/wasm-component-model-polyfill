## What to build
The review of card `2061e4` accepted `BoundaryCall` (`src/abi/boundary_call.rs`) and noted four things it did not block on. Fix them together. First, the doc on `InstanceRecord::may_leave` (`src/concurrency/instance_record.rs:29-35` at `6671fd6`) states as present fact that a built-in reading the flag traps with the cannot-leave cause, while nothing reads the flag until the built-ins land; phrase it as what the flag means and what will trap once a built-in reads it, or make it true by the time this card lands if those built-ins are in. Second, the comment at `boundary_call.rs:99-103` says the realloc's task "carries no borrow of its own, so there is nothing for an exit to check"; that is true of the realloc's own `i32` signature but not of a borrow lowered during a host call the realloc makes, which is owed to the realloc's task and which `abandon_task` does not check. Rewrite the comment to say what is actually skipped and why it is safe (the reference traps on a `canon lower` from a realloc through the may-leave flag before such a borrow exists). Third, `BoundaryCall::realloc` at `boundary_call.rs:69` returns a do-nothing guard when the tables exist but `instance.id()` is `None`, so a realloc would run with no task, no fresh thread, and the flag still set; no caller builds that combination today, so return `Error::internal` for it instead of degrading silently, as `CLAUDE.md` asks. Fourth, `run_with_probe` in `tests/baseline_realloc_task.rs:347` hard-codes the after-call snapshot's context slots to `[0; 2]` rather than reading them, so that comparison cannot fail; read them or drop the field from the after-snapshot. Add a test for a nested realloc (a realloc whose host call's result lowering calls a realloc) proving each level gets a fresh thread and the outer level's slots and flag are restored.

- [ ] The after-call snapshot in `baseline_realloc_task.rs` reads the slots it compares, and a nested-realloc test passes.
