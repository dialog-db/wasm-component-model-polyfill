## What to build
Remove the `cfg_attr(target_arch = "wasm32", ignore)` gates from the composition tests and the conformance harness. Where the browser target genuinely differs (substrate limits such as tags or GC references), record the difference in a per-target delta file (`expected-failures.web.txt`) the harness applies on top of the shared list, so the parity rule holds without hiding real gaps.

## Acceptance criteria
- [ ] No test under `tests/` carries a target gate.
- [ ] `tests web debug` runs the composition tests and the corpus and passes.
- [ ] The web delta file lists only substrate-specific differences, each with a category.
- [ ] `tests conformance` reports both targets.


## Review notes

Implementor (2026-09-15): lifting the gates exposed two more backend defects,
patched on this card in `rust/vendor/js_wasm_runtime_layer` (PATCHES.md items
3 and 4): an out-of-bounds memory read threw an uncatchable JS `RangeError`,
and a host error thrown as a JS exception was caught by the adapters'
`catch_all` and replaced by "uncaught exception". The delta file holds three
substrate lines (V8 trap wording; V8 hitting `unreachable` before the
adapter's string bounds check in two big-string cases).

One criterion is met with a caveat: `tests conformance` reports both targets,
but the browser table is *projected* from the native results plus the delta,
because wasm-bindgen's runner prints a browser test's output only when it
fails. The projection is exact while `tests web debug` passes, which is the
same command that would catch drift. The web archive's own progress test still
runs in the command to prove it passes there.
