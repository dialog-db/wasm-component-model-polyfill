## What to build
Write the PDD for a host function that holds the store across an await, Wasmtime's `LinkerInstance::func_wrap_async` (and `func_new_async`). It serves a plain WIT `func` whose host implementation is blocking async code: the future borrows the store's host data (`&mut T` or `StoreContextMut`) across its awaits, and the store runs no other work for that call until it completes.

Why it matters: PDD028 refuses Wasmtime's `async` flag on a plain import, alone or with `store`, because the polyfill has no such host function. Wasmtime's own WASI 0.3 bindings (`crates/wasi/src/p3/bindings.rs:76-97` at `v49.0.0-rc.1`) set that flag on `tcp-socket.bind`, `tcp-socket.listen`, `udp-socket.create`, `udp-socket.bind`, and `udp-socket.connect`, so `wcmp::bindgen!` cannot take Wasmtime's own `wasi:cli/command` invocation unchanged. Wasmtime's codegen corpus sets `imports: { default: async }` in two of its six option sets.

The design must settle:
1. How a future that borrows the store is parked and polled when the polyfill's host tasks are `'static` and the store drives turns (PDD018, PDD020, PDD022). Whether the store refuses other work for the duration, as Wasmtime's does.
2. The sync-lower and async-lower behaviour under each suspension provider, natively and in the browser (JSPI).
3. The generated code it enables: `Host` methods returning `impl Future + Send` (`imports: { default: async }`) and `HostWithStore` methods over `Access` (`async | store`), and the `resource_async` destructor form for `[drop]r`.
4. How the option ledger of PDD028 changes.
