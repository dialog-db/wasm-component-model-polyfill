## What to build
From the 2026-10-13 review of db2bc9. Nothing automated checks that `testWorkspace` unsets `WCMP_ZENA_REGENERATE`, `WCMP_ZENA_WEB_RUN` and `WCMP_ZENA_REPORT` (`flake.nix`, the `unset` line). Removing that line fails nothing in `tests all` or `lint`, and an inherited `WCMP_ZENA_REGENERATE` would again turn the Zena gate into a write. db2bc9 checked this by hand only.

Add a cheap check, for example a flake check or a shell test that runs the `tests zena` entry with the variable exported and a wrong stage in a copy of the record, and expects failure. Or have the Rust gate test refuse to write the record unless a variable that only `tests zena regenerate` sets is present.

## Acceptance criteria
- [x] Removing the `unset` from `testWorkspace` (or its equivalent) fails `lint` or `tests all`.
- [x] `lint` passes.

## Implementation notes

- 2026-10-13 (`test(flake): Fail a check when a lane inherits a Zena
  variable`): new flake check `test-lane-environment`. It runs every
  `tests` leaf whose script calls `cargo nextest` with stand-in `nix`,
  `git`, `wbg-pool` and `cargo`, and with the three Zena variables exported
  as `inherited`; the stand-in `cargo` records any it sees. Mutation: with
  the `unset` removed from `testWorkspace`, the check fails for every
  native, web, fidelity and zena lane. The check also found that `tests
  conformance` (`conformanceSummaryFor`) and `tests regenerate` never unset
  the variables; both now do. Those lanes run only the progress tests, so
  nothing was wrong in practice. Full `lint` green.
