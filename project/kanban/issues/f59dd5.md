## What to build

Follow-up from the second review of the PDD027 series. A `func_new` registration whose `FunctionType` the host copied from the component's own reflection (`Component::imports`) links when the type names a resource.

- **Today:** the reflection of a component that is not instantiated names each resource type by its before-instantiation identity (`ResourceType::component(n, resource i)`). `value_types_match` (`rust/wcmp/src/types/value_types_match.rs`) resolves only the declared side through the instantiation's resources, so the host side's `own<thing>` never equals the declared one, and the link fails with `TypeMismatch`.
- **Impact:** the demo carries a 100-line `host_signature` remapper (`rust/wcmp-demo/src/http_types/mod.rs`) to work around this.
- **History:** before the series, label equality made it work.
- **Wasmtime:** `func_new` takes no type, so it has no counterpart.

Resolve the before-instantiation identities of the same component on the host side too, so a type copied from the component links. Or decide that a host must build the type from its registrations, document that on `func_new`, and keep the demo's remapper.

## Acceptance criteria
- [ ] A host registers `func_new` with a `FunctionType` copied from `Component::imports`, where the type names an imported resource. The component links, and a handle crosses through the function, on both targets. Or, if the owner decides otherwise, the `func_new` docs say where the type must come from.
- [ ] The demo drops its `host_signature` remapper if the first option lands.
- [ ] `lint` passes, and `tests all` is green on both targets with the conformance summary unchanged.
