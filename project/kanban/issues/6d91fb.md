## What to build
Make the browser and native subjects exercise the Rust partner of scenarios 10 and 11 (landed as `2c71c4b6a`), so a polyfill regression on the Rust side fails the gate.

The independent review of card 8ba35a found that the web and native lines of those scenarios cannot see the partner. The record compares only stages (`wcmp-scenario/src/record.rs:108-122`), and the runner parses components in name order (`tests/zena/runner.rs:117-126`). In scenario 10 the Rust exporter parses and the Zena importer then stops at `parse`; in scenario 11 the Zena exporter stops first and the Rust importer is never parsed. A regression in how the polyfill handles the Rust component would still record `parse`, and the gate would pass. The reviewer showed, in a throwaway clone, that both partners pass today in the browser and natively when linked to each other.

Two ways to close it; the owner chooses:
- **Observe every component.** The runner parses every component of a scenario before it stops, and a partner that fails to parse is reported with its own reason, so the stage and reason name the component that failed. No new scenario.
- **A Rust-to-Rust stand-in scenario.** A scenario that links the two partners to each other at run time. PDD024 currently says "A link from Rust to Rust is not in the set. The conformance fixtures cover it", so this option changes the design.

## Acceptance criteria
- [ ] A change that breaks the polyfill's handling of the Rust partner fails `tests zena` in the browser and natively.
- [ ] PDD024 states the chosen approach.
- [ ] `tests zena`, `tests native debug`, `tests web debug` and `lint` pass.
