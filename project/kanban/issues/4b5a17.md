## What to build

The browser backend classifies JavaScriptCore's trap messages, as it
classifies V8's.

The web backend reads a trap's kind from the browser's message. In
WebKitGTK 2.54.1 (`tests webkit debug`, a23124) JavaScriptCore words the
traps differently, and these tests fail only there (each also fails on a
page of its own):

- `wcmp-wasm-core-web::contract`: `it_raises_each_core_trap_the_capabilities_permit`.
  - `indirect_call_to_null`: expected `IndirectCallToNull`, got
    `Other("call_indirect to a signature that does not match")`.
  - `bad_signature`: expected `BadSignature`, got the same message.
  - `bad_conversion_to_integer`: expected `BadConversionToInteger`, got
    `Other("Out of bounds Trunc operation")`.
  - `atomic_wait_non_shared_memory`: expected `AtomicWaitNonSharedMemory`,
    got `Other("Out of bounds memory access")`.
- `wcmp-wasm-core-web::web`:
  `it_reads_an_uncaught_exception_and_a_refused_wait_in_the_start_function`
  and `it_reads_a_trap_in_the_first_stretch_and_a_refused_wait_after_a_resumption`:
  the refused wait comes back as `Trap(Other("Out of bounds memory access"))`.

JavaScriptCore gives one message for a null entry and for a signature
mismatch, so those two may not be told apart from the message alone; the
design should say what the backend reports then. Find whether JavaScriptCore
really traps `memory.atomic.wait32` on a non-shared memory as an
out-of-bounds access, or whether the test's module meets another trap first.

## Acceptance criteria
- [x] Each trap the contract test raises is classified in WebKitGTK, or the
      contract states which kinds JavaScriptCore cannot tell apart, with
      the reason.
- [x] The two refused-wait tests pass in WebKitGTK.
- [x] `lint` passes, `tests all` is green, and `tests webkit debug` shows
      none of these tests failing.

## Review notes

- 2026-10-19 (implementer): JavaScriptCore does trap a wait on a
  non-shared memory as an out-of-bounds access: `memoryAtomicWait32`
  answers -1 for a memory that is not shared and for a thread that may
  not wait (`WasmOperationsInlines.h` lines 764-767 at 1f316fb5), and the
  baseline compiler throws `OutOfBoundsMemoryAccess` for that answer
  (`WasmBBQJIT.cpp` line 1334). The message names both in a module that
  waits, so the backend reports `Other` there. The contract test now takes
  allowances per engine (`AMBIGUOUS_IN_V8`, `AMBIGUOUS_IN_JAVASCRIPTCORE`),
  and the latter's docs state which kinds JavaScriptCore cannot tell apart
  and why (null entry vs. signature, the two truncations, the refused
  wait). The two refused-wait tests read the engine's answer. The trap
  table gains the JavaScriptCore messages the fidelity suite raised in
  WebKitGTK 2.54.1: `array.fill`/`array.copy` on a null reference, the
  instantiation's data and element segment messages, the two segment
  messages of the array instructions, and four array-segment messages that
  name several kinds. `Other` no longer carries JavaScriptCore's
  `(evaluating '...')` suffix, which names the backend's own call. README
  "Engine defects" records JavaScriptCore's ambiguous traps.

- 2026-10-19 (implementer): gates on the tip (kanban `de056af7`): `lint`
  passes, and `tests all -j 6` passes every lane, the WebKitGTK lanes
  among them (`webkit debug` 1854 tests in 103 s, `webkit no-provider`
  169 in 20 s, `fidelity webkit` 265 in 27 s).

- 2026-10-19 (peer review, round 1): ACCEPT, four non-blocking findings,
  answered: the wait citation is lines 765-768 and names the interpreter's
  slow path beside the baseline compiler; the two `Offset + array length`
  messages are noted as declared but thrown nowhere at the pinned commit
  (kept because their words name one kind, as the null-entry message is);
  the comment above the start-function wait no longer says the message
  tells the wait apart. Finding 4 (JavaScriptCore's refused wait accepts
  any `Other("Out of bounds memory access")`) is the stated cost of the
  ambiguity.

- 2026-10-19 (peer review, round 2): ACCEPT, with two cosmetic findings,
  answered: the contract comment is rewrapped, and it now cites the
  interpreter's throw in `InPlaceInterpreter64.asm` (line 10122 at
  628d6ce1850e) rather than the slow path, which only hands back -1.
  `lint` passed after the change.
