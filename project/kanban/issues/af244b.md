## What to build

The suspend seam's entry `SuspendSeam::suspend` takes `&mut Store<T>`, but a host trampoline holds only the store's tables handle (`Arc<Mutex<HandleTables>>`, see `src/linker/host_call.rs`), so the seam is not reachable from the trampoline a blocking built-in runs in; PDD018 §The Suspend Seam requires that a suspended thread resume outside any poll of a driver and that the scheduler's state be reachable from a trampoline without a driver on the stack. Reshape the entry so a trampoline can reach it with what it holds — either move what the nested turn needs behind the tables handle the way `SchedulerState` already is, or give the trampoline a handle to the scheduler — without a nested executor and without changing the seam's behaviour. Prove it with a test in which a host function called by the guest asks the seam to suspend until a host task completes, with no driver on the stack beyond the one that made the export call.

From the review of d552c8: `Store::start_host_task` has the same gap — it takes `&mut Store<T>` while a trampoline holds `&mut T` and `Arc<Mutex<HandleTables>>` — and its synchronous-lower path (`store.rs` around line 469) hard-codes the stack-switch cause instead of consulting the suspend seam's provider slot as PDD018 §Host Tasks requires ("the call succeeds ... if the suspend seam is filled on this target"). Reshape that entry with the seam so both are reachable from a trampoline, and route the synchronous-lower-with-pending-future case through the seam.

## Acceptance criteria

- [ ] A host function called by a guest export reaches `SuspendSeam::suspend` through what a trampoline holds, proved by a test on both targets.
- [ ] `start_host_task` is reachable from a host trampoline and its synchronous-lower path consults the seam's provider slot before failing with the stack-switch cause, proved by a test.
- [ ] The seam's existing tests pass unchanged.
- [ ] `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.
