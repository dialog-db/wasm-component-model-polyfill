## What to build
Add `pub async fn call_concurrent<T: 'static>(&self, accessor: &Accessor<T>, args: &[Val]) -> Result<Box<[Val]>>` to `Func` in `src/instance/func.rs` and `pub async fn call_concurrent<T: 'static>(&self, accessor: &Accessor<T>, params: P) -> Result<R>` to `TypedFunc` in `src/instance/typed_func.rs`, named as Wasmtime names them and shaped as the polyfill's own calls are. The entry reaches the store through `Accessor::with`, creates the export's task with `create_export_task`, and queues its start item behind the entry gate exactly as `Func::call` does for a synchronous export and for a callback export. It returns a future that resolves when the task's result is set, through a result channel (`attach_result_channel`), and lifts the result; post-return runs after the result is lifted, as it does for `Func::call`. The future is spawn-like, as Wasmtime documents its own: dropping it cancels nothing, and the task progresses only while a driver runs turns, in practice while the future is awaited inside the `run_concurrent` closure. A `Func::call` is a driver and cannot be entered from the closure, because it takes the store by `&mut` and the closure holds only the accessor. Two overlapping calls observe the entry gate and the scheduling order of PDD018: two calls into one callback export, where the second waits at the gate while the first runs core code, starts when the first returns a status word, and the two then interleave by events; a call into a synchronous export while a callback task of the same instance waits in its event loop, which runs at once because the exclusive thread is released between events; and a second call into a synchronous export while a first synchronous task runs, which is queued and starts when the first returns, or inside the first's nested turn when the first blocks and the two share an instance. When the store goes idle with the task unresolved, the `run_concurrent` entry returns pending and the call's future never resolves; the future does not fail on idle, because the closure can still unblock the task with another call, and a host bounds the whole entry with a timeout. From the host, reentrance while an instance is on the stack is reachable only through this entry, from a host task's body or from the `run_concurrent` closure, and the gate treats it like any other call. Re-export nothing new; the doc on each entry states the rules.

## Acceptance criteria
- [ ] Two `call_concurrent` futures into one callback export awaited together interleave by events and both resolve with their results, proved by a repository test.
- [ ] A `call_concurrent` into a synchronous export runs at once while a callback task of the same instance waits in its event loop, proved by a test.
- [ ] A second `call_concurrent` into a synchronous export is queued behind a first synchronous task and starts when the first returns, or inside the first's nested turn when the first blocks and the two share an instance, proved by tests.
- [ ] A dropped `call_concurrent` future cancels nothing: the task stays in the store and completes in a later turn, proved by a test.
- [ ] An idle store with the task unresolved leaves the `run_concurrent` entry pending rather than failing, proved by a test bounded by a timeout.
- [ ] `TypedFunc::call_concurrent` returns the typed result for the same export with no change to the host's code, and `lint` passes and `tests all` is green on both targets with the conformance summary unchanged.
