## What to build
Find out whether the project can build on the latest upstream Zena (https://github.com/elematic/zena) with no patches. If it can, move to it and retire the fork (https://github.com/cdata/zena). If it cannot, rebase the fork's patches onto the latest Zena and use that until upstream takes them.

Where things stand on 2026-10-13:
- The `zena` input already names `github:elematic/zena`, and the lock holds `1ac5684` (2026-10-05), which carries Zena's own form of the WIT reader change. No input names the fork.
- The fork's `component-target-compiler` branch carries one commit beyond Zena's `main`: `1bbe472` "[zena-compiler] Synthesize a WIT module from a document the host reads". Zena superseded it with `1ac5684`. The fork's upstream pull request is still open.
- Zena's `main` is 175 commits past the pin (`03376fd`, 2026-10-13). Two known problems at the time of card 4c4890:
  - From `91c27df` ("Make the target a property of a compile"), the compiler entry module (`zena/compiler/compiler.zena`) fails with seven type errors: `CompilerOptions` is no longer a class, and `createCompiler`, `checkCompilation` and the language service constructors changed. That port is the entry module's work, not a Zena patch.
  - From `3891263`, Zena's own flake failed on a stale `npmDepsHash`. Zena's `73682b4` "[ci] Update npmDepsHash for the current lockfile" may fix it. Check.

Steps:
1. Build Zena's latest `main` from its flake. Note any failure, and whether it is Zena's or this project's to fix.
2. Port the entry module to the new compile options (the absorbed card 3c3a33), and build the compiler component. It must still import no `wasi:filesystem` interface.
3. Run `tests zena regenerate` against the new revision, then `tests zena`. Explain any stage change.
4. If every step works on unmodified Zena: pin the `zena` input to that revision, and list what the owner needs to do to retire the fork (close the pull request, delete or archive the branch or repository).
5. If something needs a Zena change: write each change as a commit on a fork branch based on the latest Zena `main`, point the `zena` input at that branch at a pinned revision, and offer each change upstream. Follow the flake comment's patch-series rules for a fork.

    `1ac5684`.
  - **Zena's own flake:** it does not build. `nix build
    github:elematic/zena/43234db…#zena` fails in the npm fetch:
    `specified: sha256-MFx3…` against `got: sha256-XMNh…`. `73682b4` did
    update the hash, but the lockfile changed again in `9dd3aa7`, `4ac9f1d`
    and `de7264d`. That is Zena's to fix. This flake overrides only that
    fixed-output hash (`zenaPackage`, `npmDeps.overrideAttrs`), so the
    source stays Zena's, unmodified. Card f60ae7 holds the upstream issue
    text for the owner to file.
  - **This project's changes:** the entry module (`zena/compiler/compiler.zena`)
    is ported to the per-compile options of `91c27df`:
    - `CompilerOptions` is a record literal.
    - A `CompileOptions` per compile carries the world's
      `componentWrapperSynth`.
    - `checkCompilation(result, previous)`.
    - `compileComponentRuntimeModule(compiler, stdlibRoot)` runs on the
      session's compiler, and Zena caches its bytes.
    - `BinaryGenerator.interner` comes from the checker, as `compileFile`
      sets it.
    - `LanguageService` takes the target.
    The import set is unchanged: the new `zena:http/static` imports
    `wasi:filesystem`, but nothing the entry reaches imports it.
  - **One behavior lost:** `LanguageService` builds its own `{entry, target}`
    per compile and cannot take a `componentWrapperSynth`. So `check`
    against a declared world no longer reports a fault in the world's
    exports, though `compile` still does. Restoring it needs a Zena change.
    Card f099a5 holds the upstream issue text.
  - **Gates so far:** `lint zena-compiler` passes, and
    `zena-compiler-check: greeter.zena compiles to the bytes zena build
    writes`. That check also holds the import set, so there is no
    `wasi:filesystem` import. `tests zena regenerate`: Browser 18/18,
    Native 18/18, Wasmi 2/18, Wasmtime 18/18. No scenario changed stage;
    only the record's header moved to the new pin. The zena README report
    is the same, with its date and pin updated.
  - **No patch to Zena is needed, so the fork can go.** The owner's steps:
    1. Close the fork's open upstream pull request for `1bbe472`, since Zena
       took its own form of the change in `1ac5684`.
    2. Delete the fork's `component-target-compiler` branch, or archive
       `cdata/zena`.
    No input names the fork.
  - **WIT join names:** Zena's function is still `readWitSource`
    (`packages/zena-compiler/zena/lib/wit-source.zena:51`, now over
    wit-parser's `joinWitDocument`). `bundle.sh` and `source_bundle.rs`
    already use that name, and the entry's header comment now does too.
