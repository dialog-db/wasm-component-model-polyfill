## What to build

Non-blocking findings from the independent review of 10f282 (browser trap kinds, landed `769a2f56c`), in `rust/wcmp-wasm-core-web`:

- **Safari memory OOB.** JavaScriptCore uses "Out of bounds memory access" for ordinary memory bounds and for a refused atomic wait or notify, so every ordinary memory OOB reads as `Other` on Safari. A per-store flag, "a module uses atomic wait or notify", like the `shared_memory` flag, would recover `MemoryOutOfBounds` in the common case.
- **Unmapped single-kind messages.** JSC `throw_ref` on a null reference, `array.init_elem`/`array.init_data` on a null reference, SpiderMonkey "too many array elements". Add them, cited at the pinned commits.
- **Stack switching.** When Chrome enables stack switching, `continuation_already_consumed` ("WasmFX: resuming an invalid continuation", which also covers a null continuation) will need an allowance like `AMBIGUOUS`.
- **`read()`.** It turns any error whose message is in the table into a trap, even when it is not a `RuntimeError`. Fine today; say so in a comment.
- **Missing tests.** An uncaught exception from a start function; a guest trap in the first stretch of a resumable call before any suspension; `AtomicWaitNonSharedMemory` in a start function and in a resumed stack.

## Acceptance criteria
- [x] An ordinary memory OOB reads as `MemoryOutOfBounds` on JavaScriptCore when no module uses atomic wait or notify, and as `Other` otherwise.
- [x] The single-kind messages are in the table with citations and pinned in the per-engine tests.
- [x] The missing tests exist and run in the web lanes.
- [ ] `tests all` and `lint` pass.
