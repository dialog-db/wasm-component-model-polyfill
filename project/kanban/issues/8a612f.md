## What to build

Non-blocking findings from the independent review of e1b6b7 (the Wasmi backend, landed `826a38ae1`) in `rust/wcmp-wasm-core-wasmi`:

- **Host panics abort.** A host function that panics under Wasmi aborts the process on x86_64 rather than unwinding, because Wasmi's handlers are non-unwinding `extern "sysv64"` functions. Catch the panic in `call_host` (`catch_unwind`) and turn it into a `Host` trap. An unwinding panic would also skip the re-entry counter reset (`store.rs:399-416`).
- **Leaked engine slots.** `Module::new` reserves engine function slots even when compile fails, and they are freed only when the engine drops (wasmi `module/builder.rs:291`). Repeated invalid modules grow memory without bound. Bound it, or document it with a citation.
- **Hand-copied refusal modules.** `tests/wasmi.rs` holds reduced copies of the contract crate's gated modules, which will drift. Use the contract crate's own modules (see card 70bbf6).
- **Duplicated sorting.** `src/refusal.rs` duplicates `flag`/`least` from `wcmp-wasm-core-faithfulness` `suite.rs:185-230`. Share one copy.
- **Dev profile.** The `Cargo.toml` comment says every optimizing level overflows, but opt-level 1 uses the loop dispatch. Consider a crate feature that forwards Wasmi's `portable-dispatch` and `indirect-dispatch` for hosts that cannot change their profiles (wasmi-labs/wasmi#2039).

## Acceptance criteria
- [ ] A panicking host function gives a structured trap, and the re-entry counter resets.
- [ ] Repeated failed compiles do not grow memory without bound, or the limit is documented with a citation.
- [ ] The refusal tests use the contract crate's modules.
- [ ] One copy of the capability sorting.
- [ ] The profile comment is accurate, and hosts have a way around wasmi#2039 that does not need a profile change, or the docs say why not.
- [ ] `tests all` and `lint` pass.
