## What to build

Filed from card 8e4e8c (the switch review findings). In the browser, a thread that a guest call starts in place inside a host function (a nested start under the host-suspension provider that is not at rest) and that fails in its first stretch fails with a generic trap: `a thread started from inside a guest call trapped before it first suspended` (`rust/wcmp/src/concurrency/host_suspension_provider.rs`, the `None` arm of `SuspendProvider::start`). The browser settles the resumable call's promise on a microtask, and a host function cannot wait for it, so neither the guest's own trap reason nor a structured polyfill `Error` that a host import raised in that stretch reaches the caller. Natively (Wasmtime, Wasmi) the call ends on its first poll and the failure is whole. `expected-failures.web.txt` records the one corpus line it costs, `wasmtime/thread-transparency/reentrancy.wast:114`.

Let the runtime layer hand the polyfill the failure of such a call without awaiting it. The web backend already records the error of the host function that trapped a flight (`Flight::fail` in `rust/wcmp-wasm-core-web/src/flight.rs`); a synchronous way to read a settled-or-failing flight's host error, or the trap reason once the browser reports it, would let the provider return it.

## Acceptance criteria
- [ ] A nested in-place start whose first stretch calls a host import that fails with a structured polyfill `Error` fails the caller with that `Error` in the browser, proved by a web test.
- [ ] The guest-trap half either carries the engine's reason, with `reentrancy.wast:114` removed from `expected-failures.web.txt`, or the limit stays documented with the reason the browser cannot report it.
- [ ] `lint` passes and `tests all` is green on both targets.
