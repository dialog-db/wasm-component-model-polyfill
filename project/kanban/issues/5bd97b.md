## What to build

The `wasi:webgpu` spike (`~/Git/github.com/cdata/wasi-webgpu-test`) ported
`wasi-webgpu-wasmtime` 0.4.0 onto `wcmp::bindgen!`, and its ledger
(`rust/wasi-webgpu-wcmp/PORT.md`, "Other edits") lists the edits that were not
mechanical. Some are differences PDD028's "Both Targets" already lists (the `?`
at each `Accessor::with`). Decide for each of the others whether the polyfill
closes it or the design lists it, as d5c6c1 does for the dual-runtime test.

1. **`StreamProducer`'s shape.** The polyfill's has no `Buffer` associated type,
   takes `&mut StoreContext<'_, D>`, and its `Destination::set_buffer` takes a
   `Vec<T>`: the port's two producers changed their signatures, and `Some(item)`
   became `vec![item]`.
2. **`Send` on the store data.** Upstream bounds its view trait and six
   `*WithStore` impls by `Send`. In the browser `ResourceTable` is not `Send`
   (a decided design), so those bounds compile but can never be met there: no web
   host can link the port until they become `MaybeSend`. Nothing reports this
   until a host tries to link.
3. **A silent drop at `Accessor::with`.** At one site (`map-async`) upstream's
   `accessor.with(|..| -> anyhow::Result<_> {..})?;` still compiles against the
   polyfill, but the closure's own error is dropped: only the `unused_must_use`
   lint warns. A listed `?` is not enough for that case.

`StreamReader::new` taking a store context is dd9480's decision, not this
card's.

## Acceptance criteria
- [ ] Each of the three is closed in the polyfill or listed in PDD028's
      "Both Targets" (or its migration notes), with the owner's decision
      recorded here.
- [ ] For the third, a ported host that drops a closure's error at
      `Accessor::with` fails to compile, or the design says how a porter finds
      it.
