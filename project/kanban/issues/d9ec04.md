## What to build
The committed record of Zena stages, and the gate that fails a run when a stage moves.

- **The record** is one committed text file. A header names the pin (`# zena <full revision>`). Comments explain the columns and the stages. Each other line holds one scenario, one subject (`wasmtime`, `web`, or `native`), its stage, and the error text in quotes. Every subject has its own line. No overlay files.
- The record is separate from `tests/corpus/expected-failures.txt`. Its stages are not that list's categories.
- **The gate** compares stages only. The error text is for a person to read. A run fails when:
  - a subject's stage differs from the record, in either direction (a scenario that passes where the record has a failing stage fails too);
  - the record has no line for a scenario, or a line for a scenario that does not exist;
  - the pin in the header differs from the revision the build passes in from the flake lock. The message names both revisions.
- A `compile` stage is the same for every subject, and nothing else runs.
- Commit the record lines for scenario 1.

Notes from the review of f3f4c8 (landed as `781501750`):
- Nothing yet fails when scenario 1 stops compiling: `scalar.status = 0` is not gated. The record's `compile` stage is the first gate on it.
- `tests/zena/build.sh` records any nonzero exit of `zena` as a refusal, including exit 127 (no toolchain) or a crash. The `compile` stage reads it the same way unless this card decides otherwise.
- A scenario with WIT compiles with `--wit wit --world <program stem>`.

Notes from the review of 264c89 (landed as `b882bd371`):
- The cross-target mismatch test (`tests/zena.rs:110-138`) passes without testing anything if scenario 1 stops passing on a subject: the loop skips it and only prints, and neither nextest nor the browser shows the print. `zena.rs:83` asserts no stage either. The record and gate are the first check that fails when scenario 1 regresses on a subject; compare `Report` values inside the test, because a passing browser test cannot print.
- Real Zena console output stops at `parse` on both polyfill subjects, not `instantiate`: the polyfill compiles core modules inside `Component::new`. Web gives 'reference type (ref null (module 8)) is not supported', native 'tags are not supported', both under the text 'instantiation error'. PDD024's example record predicts `instantiate` for tag refusals. Record what the runner observes; the owner has been told.

## Acceptance criteria
- [x] A record in which one subject's stage is one step later than the real run fails the run. A record in which it is one step earlier fails the run.
- [x] A record with a missing line and a line for a scenario that does not exist fails the run once for each line.
- [x] A record whose header names a different revision from the flake lock fails with a message that names both revisions, even when every stage matches.
- [x] A test scenario whose program does not compile records `compile` for all three subjects. Its build succeeds, and the record keeps Zena's error output.
- [x] `tests native debug` and `tests web debug` pass.
- [x] `lint` passes.
