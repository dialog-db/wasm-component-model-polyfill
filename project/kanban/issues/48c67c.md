## What to build
Write the PDD for integration tests that compile real Zena programs to components with Zena's own toolchain and then drive them through the polyfill on both targets.

**Why.** Zena (https://zena-lang.dev/, `github:elematic/zena`) is a young WasmGC language that changes daily. Its component target (`zena build --target component`, with `--wit` and `--world`) emits WasmGC core modules inside a linear-memory Canonical ABI shell. That shell has `utf8` strings, callback-lifted async exports, p2 stdio imports, and p3 `wasi:clocks` imports (Zena's `docs/design/component-emission.md`). The owner's goal is an in-browser tool that compiles Zena programs to components and tests them on the polyfill. Hand-written WAT that imitates Zena's output goes stale within days. Only the toolchain gives ground truth. So the tests must use a pinned Zena toolchain and record what happens, not assert success.

**Context for the design.** Code reading suggests these failures. None is proven yet:
- Both runtime-layer backends refuse a core module that exports a tag. Zena exports `__zena_exception` whenever a program uses exceptions (`zena-compiler/zena/lib/codegen/wasm-module.zena:1688`).
- The browser backend refuses any defined global of a GC reference type (`rust/vendor/js_wasm_runtime_layer/src/module.rs`, global section).
- GC-typed exports, if any survive into the component target, fail the export type conversion on both backends.

The PDD must settle these questions:

1. **Relationship to the conformance suite.** PDD016 and card 657c60 use committed fixtures, which the `fixtures` command rebuilds from a real toolchain. Decide whether Zena fixtures follow that model or get built from a pinned toolchain at build time with nothing committed. Give the reason, weighing ground truth against stability and build cost.
2. **Pinning the toolchain.** Decide how the Zena toolchain enters the build (for example, a flake input for Zena's `packages.zena`), how the pin moves, and whether it follows this flake's `nixpkgs`. Zena's package also builds its own Rust/Wasmtime runner, so state the build cost and cache behavior.
3. **The reference run.** Decide how each scenario runs under Wasmtime's own component API natively, as the oracle. The oracle separates "the polyfill cannot run it" from "the program or Zena's output is wrong". Say how a scenario that fails under Wasmtime is classified.
4. **The outcome model.** Define the stages a scenario can stop at: compile, reference, `Component::new`, link, instantiate, call, or pass. Say how outcomes and error text are recorded on each target, how a change in either direction fails the gate, and how the record is regenerated. A Zena compile failure must be a recorded outcome, not a broken build. Relate the format to `expected-failures.txt` and its overlays.
5. **Scenarios.** Set the first set, the criteria for a scenario, and how a contributor adds one. The candidates are:
   1. A scalar export called both untyped and typed.
   2. A string in and a string out.
   3. GC classes and arrays used internally.
   4. Exceptions, both caught inside the program and uncaught.
   5. Console output through the p2 stdio imports.
   6. An async export that sleeps on a p3 timer.
   7. A custom world through `--wit` and `--world` that imports a host function.
6. **Host imports.** Decide how the tests supply the WASI imports Zena components use. In-test host functions can do it today. Say what changes once the minimal WASI host (da3054) exists.
7. **Moving the pin.** Say who moves the pin and how, and what a pin move that changes outcomes requires: a regenerated record, and follow-up cards for new failures.
8. **Reporting.** Decide how the compatibility table for both targets is presented, for example as a menu leaf, in the README, or both.
9. **Generality.** Decide whether the mechanism is Zena-specific or a general pattern for testing against external language toolchains, such as other WasmGC or component-emitting compilers. Record that as a goal or a non-goal.

Non-goals to consider: fixing any failure the scenarios find (each root cause gets its own card), and running the Zena compiler itself inside the polyfill.

The PDD follows `project/design/README.md`: plain English, the six sections, Goals and Non-goals that express scope, and Test Cases that a later card can lift as acceptance criteria. Do not name later PDDs. Engineering planning decides file names and directory layout.

## Acceptance criteria
- [ ] The PDD is formatted with `markdown format` and passes the `markdown` flake check.
- [ ] It answers questions 1 to 9, each with its reason. Claims about Zena's output cite Zena's source or design documents at the revision read.
- [ ] Its Test Cases cover:
  - a scenario compiled from the pinned toolchain running under the reference and under the polyfill on both targets
  - a Zena compile failure recorded as an outcome
  - an outcome change in either direction failing the gate
  - regeneration of the record after a pin move
  - each suspected failure above confirmed or refuted by a scenario
- [ ] The owner accepts the PDD before any implementation card is filed.
