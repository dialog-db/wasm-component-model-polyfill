## What to build
Build the switch module in its stack-switching form, and the switch probe that selects the stack-switching provider natively.

**The provider contract.** Replace today's `SuspendProvider` trait (`src/concurrency/suspend_provider.rs`) with PDD022's contract. A provider must: start a thread entry on a stack of its own, from the scheduler or from inside a trampoline; suspend the running thread when a blocking built-in is not ready, with only WebAssembly frames between the start of that stack and the point of suspension; resume a suspended thread later with the result of the built-in it suspended in; keep any number of threads suspended at once and resume them in any order; report to the caller whether a thread entry finished or suspended, at the moment it does so; and drop a suspended thread without resuming it when its store drops, with no destructor run. A mechanism that cannot meet all six is not a provider.

**The switch module.** The polyfill generates one small core module for each store. It builds the bytes in memory and never fetches them. It has a shim for each blocking built-in, which a guest imports in place of the host trampoline, and an entry wrapper for each thread entry:

```text
shim for a blocking built-in B:
    loop:
        status = host.try_B(args)        // returns at once, never blocks
        if status is ready:
            return host.finish_B()       // the result the guest reads
        suspend                          // the provider's own form of suspend

entry wrapper for a thread entry E:
    results = E(args)
    host.finished(thread, results)       // the scheduler reads these at once
```

The stack-switching form defines one control tag and one table of continuations, and exports a start and a resume function to the scheduler (`cont.new`, `resume` on the tag, `suspend` in a shim). A resumption runs synchronously.

**The probe.** A module of about 130 bytes, carried as a constant in the polyfill binary. It starts one thread, suspends it, resumes it, and makes sure it finished. An engine that rejects the module, or that runs it with any other outcome, fails the probe. `Engine::new` runs it first in the selection order and stays synchronous.

**The Wasmtime backend.** Turn on the stack-switching proposal in the vendored `wasmtime_runtime_layer`'s engine configuration, with the `wasmtime` cargo feature it needs, where Wasmtime 49 implements it: x86_64 Linux. Record the change in its `PATCHES.md`. The feature turns off compiler inlining; note the cost. Check that `wasm_runtime_layer` passes the continuation types of the switch module through its module parsing.

This card does not yet run guest threads through the provider. Its own test proves the risky part first: the switch module next to real core instances and a nested resume from a host frame.

## Acceptance criteria
- [ ] On the x86_64 Linux host the native engine's query answers the stack-switching provider, and with the provider turned off it answers none, each proved by a repository test.
- [ ] A repository test proves the probe's failure path: a probe that does not finish selects no provider.
- [ ] A repository test runs the generated switch module with two core instances: a thread suspends in a shim with a frame of the other instance between, a host function running inside that thread starts a second thread that suspends, the host function returns, and both threads resume later in either order and finish.
- [ ] The provider contract, the switch module, and the probe are documented where they live, with the design context inline.
- [ ] `lint` passes and `tests all` is green on both targets, any directive that starts passing has its line removed from the expected-failure list, and every line whose reason this card changes is refreshed from a live run.
