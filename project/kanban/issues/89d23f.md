## What to build
`Func::start_concurrent` starts a synchronously lifted export's task with `async_function = false` (`src/instance/func.rs:532`), whatever the export's function type. The comment above it (`:525-530`) states the rule correctly — the entry gate applies to a task whose function type is `async`, which a synchronous lift can carry — and the `call_async` path passes `self.signature.async_` (`:302`). So an async-typed, sync-lifted export started through `call_concurrent` never waits at the entry gate and never takes the instance exclusively.

The spec requires both. `Task.needs_exclusive` is `not opts.async_ or opts.callback` for an async-typed function, and `enter_implicit_thread` waits while backpressure is set or another thread holds the instance exclusively, then takes it (`canonical-abi/definitions.py:416-436`); `WaitableSet.wait` keeps `exclusive_thread`. Wasmtime holds an async-typed `StartImplicit` while `do_not_enter` is set (`crates/wasmtime/src/runtime/component/concurrent.rs:769-771, 2072-2086`). Under both, a second concurrent call of such an export waits at the gate until the first task leaves.

Found by the reviewer of card `2b062e`, whose first test pinned this behaviour: two concurrent calls of one async-typed, sync-lifted export that block in `waitable-set.wait` both ran (native log `[1,10,11,2]`, where the spec gives `[1,2,10,11]`), and in the browser the second was refused as a re-entrant host call instead of waiting.

Pass the export's function type on this path, as `call_async` does.
