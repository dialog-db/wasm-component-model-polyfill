## What to build

The WebKitGTK lanes match the Chrome lanes that replay the web debug
archive: `tests webkit no-provider` runs the conformance corpus with the
suspend provider turned off, and `tests fidelity webkit` runs the
specification test suite on the browser backend in JavaScriptCore.

`tests webkit debug` (a23124) runs the default profile only. Chrome's web
debug archive also runs under the `no-provider` profile (`tests web
no-provider`) and the `fidelity` profile (`tests fidelity web`). Both
profiles already work through the WebKit script, since its arguments reach
`cargo nextest list` (`tests webkit debug --profile no-provider`), but no
menu leaf names them and nothing gates them.

The fidelity suite holds a backend to its cited expected failures, and the
browser backend's list (`rust/wcmp-wasm-core-web/tests/fidelity/expected-failures.txt`)
is V8's. JavaScriptCore needs a list of its own, chosen by the engine the
suite runs in, with each entry cited to WebKit's source or bug tracker as
the V8 entries are cited to V8's. The spike (0ef2ae) found, before the
JavaScriptCore trap table existed, 239 of 264 scripts passing: most
failures were trap kinds read as `Other`, about 70 were invalid modules
JavaScriptCore compiles, and a handful were value mismatches.

The release archive stays out: a release build changes the polyfill's code
and not what the browser's engine does (a23124's notes).
